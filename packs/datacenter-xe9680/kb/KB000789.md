# PSU Redundancy Loss on PowerEdge XE9780L — Detection and Response

| | |
|---|---|
| **Article ID** | KB000789 |
| **Version** | 4 |
| **Last updated** | 2025-08-19 |
| **Classification** | Break/Fix — Power Infrastructure |
| **Default severity** | Critical (Sev 2 — node still serving) |
| **Audience** | Datacenter operations, facilities |
| **Applies to** | Dell PowerEdge XE9780L (all GPU configurations) |

## Summary

The XE9780L runs four hot-swappable power supplies in a 2+2 redundant grid configuration, with each pair fed from a separate PDU (A/B feed). Loss of a single PSU — whether from a power supply failure or loss of its AC input — degrades redundancy but does not interrupt service. However, under full GPU load the remaining supplies may not cover total system draw, in which case the iDRAC automatically engages GPU power capping, reducing training throughput. Loss of a second PSU in the same redundancy group risks an unplanned system shutdown, so a degraded-redundancy state must be resolved promptly rather than tolerated.

## Affected products

- Dell PowerEdge XE9780L, all GPU configurations
- Both PDU-fed and breaker-panel-fed rack power layouts

## Error signature

The canonical signatures for this fault are:

- `PSU 2 input lost`
- `power supply failure`

iDRAC Lifecycle Log message IDs: `OEM.1.0.PSULost` (severity Critical), often preceded by `PSU.1.0.InputVoltageWarning`. The slot number in the message identifies the affected supply.

## Symptoms

- iDRAC Lifecycle Log records `OEM.1.0.PSULost` with severity Critical
- The affected PSU's status LED on the chassis rear is amber or unlit
- iDRAC Dashboard shows the PSU as `Failed`, `Absent`, or `Input Lost`
- If system draw exceeds remaining capacity, iDRAC logs `Power budget exceeded` and DCGM reports GPU power limits reduced (e.g. capped from 400 W to 300 W), with a corresponding drop in training throughput
- An input-voltage warning (`PSU.1.0.InputVoltageWarning`) in the minutes before the loss points at the facility feed rather than the PSU itself

## Sample log excerpt

Representative sequence from a production occurrence on `gpu-server-01` (03:11 local — note the voltage sag preceding the loss):

```
03:10:00Z INFO  iDRAC[LifecycleLog]: System power healthy. PSU 1: 1100W, PSU 2: 1100W, PSU 3: 1100W, PSU 4: 1100W
03:10:30Z INFO  iDRAC[LifecycleLog]: GPU workload steady. Total system draw: 3840W of 4400W available
03:11:45Z WARN  iDRAC[LifecycleLog]: PSU.1.0.InputVoltageWarning — PSU 2: input voltage fluctuation detected (199V, threshold 200V)
03:11:47Z CRIT  iDRAC[LifecycleLog]: PSU 2 input power lost — redundancy degraded
03:11:47Z CRIT  iDRAC[LifecycleLog]: OEM.1.0.PSULost — Power supply failure on PSU 2. System now operating on 3 of 4 PSUs.
03:11:48Z INFO  iDRAC[LifecycleLog]: Remaining capacity: PSU 1 (1100W), PSU 3 (1100W), PSU 4 (1100W) = 3300W. Current draw 3840W — OVER CAPACITY
03:11:49Z CRIT  iDRAC[LifecycleLog]: Power budget exceeded. Initiating GPU power capping.
03:11:49Z WARN  dcgm[1234]: GPU power limits reduced: all GPUs capped at 300W (was 400W)
```

In this incident the system draw (3840 W) exceeded remaining capacity (3300 W), so the iDRAC capped GPU power automatically — expected protective behavior, not a second fault.

## Impact

- **Workload impact:** None immediately — the node keeps running on the remaining supplies and no drain or migration is required. If automatic GPU power capping engages, training throughput drops roughly in proportion to the cap (a 400 W → 300 W cap typically costs 15–25% throughput) until redundancy is restored.
- **Service risk:** Degraded power redundancy until the PSU or its feed is restored. A second PSU loss in the same redundancy group during this window can force an unplanned shutdown of the entire node, hard-killing all 8 GPUs' workloads without checkpoint.
- **Estimated remediation duration:** ~5 minutes for triage and acknowledgment, plus a scheduled maintenance window for the physical fix (PSUs are hot-swappable; no downtime required for replacement).

## Root cause

Determine feed vs. hardware first — it changes who owns the fix:

1. **Loss of PDU feed** to the PSU's AC input (facilities issue: PDU breaker, upstream panel, or utility transfer event). Indicated by `Input Lost` state and often a preceding `InputVoltageWarning`; the PSU itself is healthy.
2. **PSU hardware failure** (internal fault). Indicated by `Failed` state with the AC feed confirmed live at the receptacle.
3. **Tripped rack branch circuit breaker** for that PSU's circuit. Check whether other equipment on the same branch dropped at the same timestamp.

## Remediation steps

### Step 1 — Acknowledge PSU fault in iDRAC (`acknowledge_alert`)

Acknowledge the active alert so escalation paging stops while the physical investigation proceeds. Export the SEL before clearing it — it is the primary evidence for a Dell dispatch:

```bash
racadm lclog export -f psu_incident_$(date +%Y%m%d).xml
racadm clrsel
```

Or via iDRAC UI: Maintenance → System Event Log → Save, then Clear. Do not silence PSU monitoring itself — a second PSU event in this window must page immediately.

### Step 2 — Schedule PSU replacement with facilities (`schedule_maintenance`)

1. Identify the faulted slot and state:

   ```bash
   racadm getsensorinfo | grep -iA2 "PS[0-9]"
   ```

   (or iDRAC UI → Power → Power Supplies). Note whether the state is `Input Lost` (feed problem) or `Failed` (hardware).

2. **If Input Lost:** dispatch facilities to check the PDU outlet and rack branch breaker for that feed. Restoring the feed typically clears the fault within seconds with no part replacement.
3. **If Failed with feed confirmed live:** raise a Dell hardware dispatch for a replacement PSU. XE9780L PSUs are hot-swappable — schedule the swap as a low-risk window; no node drain is needed, but the swap should not proceed while the system is in an over-capacity/power-capped state at full load.

### Step 3 — Confirm remaining PSU load within limits (`verify_redundancy`)

While running degraded, confirm the surviving supplies can carry the load:

```bash
racadm getsensorinfo | grep -i "psu\|watt"
```

If current draw exceeds remaining PSU capacity (as in the excerpt above), the iDRAC will already have capped GPU power; you may cap explicitly to a known-safe value instead of relying on the automatic budget:

```bash
nvidia-smi -pl 300    # applies to all GPUs; sets 300 W cap
```

After the PSU or feed is restored, verify redundancy is re-established (`racadm getsensorinfo` shows all four PSUs `Present`/`OK` and the Lifecycle Log records redundancy regained), then restore full GPU power:

```bash
nvidia-smi -pl 400
```

## Escalation

- Feed confirmed live but PSU still shows `Failed` → Dell on-site dispatch for hot-swap replacement. Provide the exported Lifecycle Log and `racadm getsensorinfo` output.
- Repeated `InputVoltageWarning` events across multiple nodes on the same PDU feed → escalate to facilities/electrical as a shared-infrastructure problem before it produces simultaneous multi-node PSU losses.
- Second PSU loss on the same node while degraded → treat as Sev 1: begin an orderly node drain immediately to protect against unplanned shutdown.
