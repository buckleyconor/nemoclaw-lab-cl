# GPU Xid 79: GPU Has Fallen Off the Bus — Detection and Remediation

| | |
|---|---|
| **Article ID** | KB000123 |
| **Version** | 6 |
| **Last updated** | 2025-11-14 |
| **Classification** | Break/Fix — GPU Hardware |
| **Default severity** | Critical (Sev 1) |
| **Audience** | Datacenter operations, GPU platform SRE |
| **Applies to** | Dell PowerEdge XE9780L, NVIDIA B300 SXM6 288 GB |

## Summary

Xid 79 indicates that the NVIDIA driver has lost PCI Express communication with a GPU. The device stops responding to memory reads and configuration cycles — it has effectively "fallen off the bus." The GPU is no longer usable by any workload, `nvidia-smi` can no longer enumerate it, and any process holding a CUDA context on the device will fail. This is a fatal, non-recoverable fault at the driver level: the device cannot be restored without a reset or full power cycle, and recurrence after reset indicates failing hardware.

## Affected products

- Dell PowerEdge XE9780L with 8× NVIDIA HGX B300 SXM6 288 GB GPUs (1100 W per GPU, direct liquid cooled)
- NVIDIA data center driver branch R570 or later, the minimum for Blackwell Ultra (confirm with `nvidia-smi --query-gpu=driver_version --format=csv,noheader`)
- All supported OS releases (Ubuntu 22.04 LTS, RHEL 9.x)

## Error signature

The canonical signatures for this fault are:

- `Xid 79`
- `GPU has fallen off the bus`

Kernel ring buffer (`dmesg` / `journalctl -k`):

```
NVRM: Xid (PCI:0000:3b:00): 79, pid='<unknown>', name=<unknown>, GPU has fallen off the bus.
```

iDRAC Lifecycle Log message IDs: `OEM.1.0.GPUFault`, `GPU.1.0.GpuXidError` (severity Critical).

## Symptoms

- iDRAC Lifecycle Log records event `OEM.1.0.GPUFault` with severity Critical
- DCGM health watch reports `GPU has fallen off the bus` and marks the GPU failed (`GPU_XIDDB_79`), then removes the device from its watch list
- `nvidia-smi` returns `Not Found` for the affected GPU UUID, or hangs for the affected index
- Kernel log contains `NVRM: Xid (PCI:<bus>): 79`
- The device disappears from `lspci` output for its bus address
- CUDA applications on the device terminate with `CUDA_ERROR_DEVICE_UNAVAILABLE` or hang in kernel launch
- Kubernetes device plugin decrements `nvidia.com/gpu` allocatable on the node

## Sample log excerpt

Representative sequence from a production occurrence on `gpu-server-02` (DCGM + kernel + iDRAC, correlated by timestamp):

```
09:22:15Z INFO  nvidia-smi[1235]: All 8 GPUs reporting healthy state
09:23:38Z WARN  kernel[  583.447211]: pciehp 0000:00:1c.7:pcie204: Slot(204): Attention button pressed
09:23:39Z WARN  kernel[  584.101834]: pciehp 0000:00:1c.7:pcie204: Slot(204): Card not present
09:23:40Z CRIT  kernel[  584.882043]: NVRM: Xid (PCI:0000:3b:00): 79, pid='<unknown>', name=<unknown>, GPU-60ded90b-1a2b-3c4d-5e6f-7a8b9c0d1e2f
09:23:40Z CRIT  dcgm[1234]: GPU 0 (bus 0x3b): GPU has fallen off the bus — Xid error 79
09:23:40Z CRIT  dcgm[1234]: GPU 0 health FAILED: GPU_XIDDB_79
09:23:41Z ERROR iDRAC[LifecycleLog]: GPU.1.0.GpuXidError — GPU 0 critical Xid 79 fault detected (PCI 0000:3b:00)
09:23:41Z CRIT  nvidia-smi[1235]: GPU-60ded90b-1a2b-3c4d-5e6f-7a8b9c0d1e2f: Not Found (Xid 79)
09:23:43Z ERROR dcgm[1234]: Removing GPU 0 from health watch — device lost
```

Note the `pciehp` "Card not present" events immediately preceding the Xid — loss of PCIe link presence is the defining precursor and distinguishes Xid 79 from software-recoverable Xids (13, 31, 43).

## Impact

- **Workload impact:** All jobs bound to the failed GPU terminate or hang immediately. Multi-GPU jobs spanning the device (NCCL process groups) will time out and must restart from their last checkpoint. Remediation requires draining the full node, so all workloads on the node — not just those on the failed GPU — are checkpointed and rescheduled.
- **Service risk:** Cluster capacity is reduced by one 8-GPU node for the duration of remediation. No impact to other nodes.
- **Data risk:** None to data at rest. In-flight results on the failed device since the last checkpoint are lost.
- **Estimated remediation duration:** 15–20 minutes (drain + power cycle + health verification), assuming the fault does not recur.

## Root cause

Xid 79 is a symptom of PCIe link loss, not a single root cause. Field occurrences break down approximately as follows:

1. **PCIe signal integrity fault** — degraded riser, connector, or PCB trace. Most common cause of *recurring* Xid 79 on the same slot.
2. **GPU firmware/microcontroller crash** dropping the PCIe link. Typically a one-off; resolved by power cycle.
3. **Power delivery transient** on the GPU 12 V rail (correlate with iDRAC PSU/voltage events in the same window — see [KB000789](KB000789.md)).
4. **Thermal runaway** causing the device to assert a fatal shutdown (correlate with prior `OEM.1.0.ThermalThrottle` events — see [KB001213](KB001213.md)).

A single isolated occurrence is treated as transient; a second occurrence on the same GPU within 30 days is treated as hardware and dispatched.

## Remediation steps

### Step 1 — Cordon and drain affected node (`drain_node`)

Prevent new scheduling and migrate existing workloads:

```bash
kubectl cordon gpu-server-02
kubectl drain gpu-server-02 --ignore-daemonsets --delete-emptydir-data --timeout=600s
```

Confirm the drain completed before proceeding — a reset with live CUDA contexts on the surviving GPUs will fault them as well:

```bash
kubectl get pods --field-selector spec.nodeName=gpu-server-02 -o wide
```

Only DaemonSet pods (monitoring, device plugin) should remain.

### Step 2 — Issue GPU reset via iDRAC (`gpu_reset`)

A driver-level reset (`nvidia-smi --gpu-reset`) will fail for Xid 79 because the driver can no longer reach the device. A full power cycle via iDRAC is required to force PCIe re-enumeration:

```bash
racadm serveraction powercycle
```

Allow 5–8 minutes for POST and GPU enumeration on the XE9780L (8× SXM6 initialization is slow). Confirm the device has re-enumerated:

```bash
lspci -d 10de: | grep -c 3D    # expect 8
nvidia-smi -L                  # expect all 8 GPUs listed with UUIDs
```

If the GPU does not reappear after power cycle, stop here and escalate (see below).

### Step 3 — Re-run DCGM health check (`verify_health`)

Validate the node before returning it to the scheduler pool:

```bash
dcgmi health -g 0 -s a         # enable all health watches
dcgmi diag -r 2                # medium diagnostic (~5 min): PCIe, memory, SM stress
```

All tests must report `Pass`. Additionally verify the PCIe link came back at full width and speed — a link that retrained at reduced width is a signal-integrity red flag:

```bash
nvidia-smi --query-gpu=index,pcie.link.gen.current,pcie.link.width.current --format=csv
# expect Gen5 / x16 on every GPU
```

Once clean, uncordon:

```bash
kubectl uncordon gpu-server-02
```

Continue monitoring the node's DCGM health for 24 hours before considering the incident closed.

## Escalation

Escalate to Dell hardware support (Sev 2 dispatch) if any of the following hold:

- The GPU does not re-enumerate after a full power cycle
- Xid 79 recurs on the same GPU within 30 days
- PCIe link retrains at reduced width/speed after reset

Attach to the case: iDRAC Lifecycle Log export (`racadm lclog export`), `dmesg` covering the event, `nvidia-bug-report.sh` output, and the DCGM diag results. Request PCIe riser inspection and, for recurrence, GPU tray replacement.
