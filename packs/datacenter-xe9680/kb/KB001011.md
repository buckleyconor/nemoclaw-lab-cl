# NVLink Fabric Link Failure on XE9780L — Detection and Remediation

| | |
|---|---|
| **Article ID** | KB001011 |
| **Version** | 5 |
| **Last updated** | 2025-10-08 |
| **Classification** | Break/Fix — GPU Interconnect |
| **Default severity** | Critical (Sev 1) |
| **Audience** | Datacenter operations, GPU platform SRE, ML infrastructure |
| **Applies to** | Dell PowerEdge XE9780L with NVSwitch-based NVLink fabric (H100 SXM5) |

## Summary

The XE9780L connects its 8 H100 GPUs through an NVSwitch fabric providing 900 GB/s of bidirectional bandwidth per GPU. An NVLink fabric failure (`nvlink_recovery_error`) means at least one inter-GPU link has taken errors beyond the recoverable threshold and entered recovery mode. The consequences are worse than the "one link down" framing suggests: NCCL collectives route across the full fabric, so a degraded link causes distributed training jobs to hang at the next collective operation (AllReduce/AllGather timeout) or — if NCCL silently falls back to PCIe paths — to run at a fraction of expected throughput. Treat any fabric error on a node running distributed workloads as a whole-node fault.

## Affected products

- Dell PowerEdge XE9780L with NVSwitch-based NVLink fabric
- Both bare-metal and Kubernetes-scheduled distributed workloads (NCCL, NVSHMEM)

## Error signature

The canonical signatures for this fault are:

- `NVLink fabric failure`
- `nvlink_recovery_error`

Kernel ring buffer:

```
NVRM: nvlink_recovery_error on NVSwitch port 4 (GPU 0, link 0)
```

iDRAC Lifecycle Log message IDs: `OEM.1.0.NVLinkDown`, `GPU.1.0.NVLinkFabricLinkDown` (severity Critical). DCGM reports `NVLink error count exceeded threshold on GPU pair (<i>,<j>)`.

## Symptoms

- iDRAC Lifecycle Log records `OEM.1.0.NVLinkDown` with severity Critical
- Kernel log contains `nvlink_recovery_error` identifying the NVSwitch port, GPU, and link index
- `nvidia-smi nvlink --status` shows one or more links `Inactive` or in error state
- DCGM NVLink error counters (CRC, replay, recovery) exceed threshold on a GPU pair
- NCCL jobs report `NCCL WARN Watchdog caught collective operation timeout` or hang without output; NCCL AllReduce latency jumps from single-digit ms to timeout
- Elevated NVSwitch port CRC error rates in the minutes before the failure are the typical precursor

## Sample log excerpt

Representative sequence from a production occurrence on `gpu-server-02` — note the CRC error-rate warning ~10 seconds before the link drops:

```
11:03:00Z INFO  nvidia-smi[1235]: NVSwitch 0: fabric throughput 6.8 TB/s
11:04:15Z WARN  nvidia-smi[1235]: NVSwitch 0: Port 4 (GPU0): CRC error rate elevated — 1.2e-6 (threshold 1e-6)
11:04:20Z WARN  nvidia-smi[1235]: NVSwitch 0: Port 4 entering recovery mode
11:04:22Z CRIT  dcgm[1234]: NVLink fabric failure: link GPU0<->GPU1 is down (nvlink_recovery_error)
11:04:22Z CRIT  kernel[  743.009812]: NVRM: nvlink_recovery_error on NVSwitch port 4 (GPU 0, link 0)
11:04:22Z CRIT  dcgm[1234]: DCGM: NVLink error count exceeded threshold on GPU pair (0,1)
11:04:23Z ERROR iDRAC[LifecycleLog]: OEM.1.0.NVLinkDown — NVLink fabric failure detected. GPU 0 link 0 down. Severity: Critical.
11:04:24Z WARN  dcgm[1234]: NCCL AllReduce timeout — NVLink unavailable for GPU 0,1
```

## Impact

- **Workload impact:** Multi-GPU jobs on the node hang or abort at the next collective operation and must restart from checkpoint. The node must be fully drained before fabric reset — resetting NVLink under live NCCL process groups corrupts in-flight collective operations. Single-GPU jobs are technically unaffected but are drained anyway as part of node remediation.
- **Service risk:** One 8-GPU node out of the pool for the duration (~20 minutes). Distributed training jobs spanning this node restart from their last checkpoint on remaining capacity.
- **Data risk:** A silently degraded fabric (NCCL falling back to PCIe) does not corrupt data but can waste large amounts of compute at reduced throughput before anyone notices — which is why throughput verification (Step 3) is mandatory before uncordon.
- **Estimated remediation duration:** ~20 minutes (drain + power cycle + fabric verification).

## Root cause

1. **NVSwitch port signal integrity** — CRC errors from PCB trace or connector degradation. The elevated-CRC-then-recovery pattern in the excerpt above is the classic signature; recurrence on the same port after power cycle confirms hardware.
2. **GPU-side NVLink PHY fault** — errors attributed consistently to one GPU across *different* switch ports implicate the GPU rather than the switch.
3. **GPU or NVSwitch firmware fault** — typically a one-off, cleared by power cycle; check firmware currency against the Dell support matrix while remediating.
4. **Thermal event** causing link instability — correlate with `OEM.1.0.ThermalThrottle` events in the same window (see [KB001213](KB001213.md)).

## Remediation steps

### Step 1 — Cordon and drain affected node (`drain_node`)

```bash
kubectl cordon gpu-server-02
kubectl drain gpu-server-02 --ignore-daemonsets --delete-emptydir-data --timeout=600s
```

Verify no NCCL process groups remain before touching the fabric — a fabric reset under live collectives leaves peer ranks hung on other nodes:

```bash
kubectl get pods --field-selector spec.nodeName=gpu-server-02 -o wide
nvidia-smi --query-compute-apps=pid,process_name --format=csv   # expect empty
```

### Step 2 — Reset NVLink fabric via iDRAC (`nvlink_reset`)

Individual link retraining is not exposed on the SXM/NVSwitch platform; a full power cycle is the reliable way to reset the NVSwitch fabric and retrain all links:

```bash
racadm serveraction powercycle
```

Allow 5–8 minutes for POST, GPU enumeration, and Fabric Manager startup. Confirm Fabric Manager came up cleanly — GPUs on an NVSwitch system are unusable for peer-to-peer traffic without it:

```bash
systemctl status nvidia-fabricmanager
journalctl -u nvidia-fabricmanager --since "-10 min" | tail -20   # expect "Successfully configured all the available NVSwitches"
```

### Step 3 — Verify fabric recovery (`verify_fabric`)

Check that every link on every GPU has returned to `Active`:

```bash
nvidia-smi nvlink --status          # all GPUs; every link should report full speed
dcgmi nvlink -g 0 --link-status     # DCGM view: expect all links "Up", error counters 0
```

Link state alone is not sufficient — a link can train `Active` at degraded quality. Confirm actual fabric throughput with an NCCL bandwidth test (nccl-tests):

```bash
/opt/nccl-tests/build/all_reduce_perf -b 1G -e 1G -f 2 -g 8
```

Expected bus bandwidth on a healthy 8× H100 NVSwitch node is ~450–480 GB/s for large messages. A result significantly below that (or a hang) means the fabric is still degraded — do not uncordon; escalate. On a clean result:

```bash
kubectl uncordon gpu-server-02
```

Keep the DCGM NVLink error counters under watch for 24 hours.

## Escalation

Engage Dell support for NVSwitch diagnostics if:

- `nvlink_recovery_error` recurs on the same NVSwitch port after a power cycle (port/tray hardware)
- Errors follow one GPU across different ports (GPU-side PHY — GPU tray replacement)
- The NCCL bandwidth test stays below expected throughput with all links nominally `Active`

Attach: `nvidia-smi nvlink --status` output, DCGM NVLink error counters, Fabric Manager journal, iDRAC Lifecycle Log export, and the nccl-tests results. Reference the elevated CRC rate history if present — it materially speeds Dell's triage.
