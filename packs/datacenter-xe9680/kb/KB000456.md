# GPU HBM Uncorrectable ECC Error (DBE) — Detection and Remediation

| | |
|---|---|
| **Article ID** | KB000456 |
| **Version** | 5 |
| **Last updated** | 2025-09-30 |
| **Classification** | Break/Fix — GPU Memory |
| **Default severity** | Critical (Sev 1) |
| **Audience** | Datacenter operations, GPU platform SRE |
| **Applies to** | Dell PowerEdge XE9780L, NVIDIA B300 SXM6 288 GB (HBM3E) |

## Summary

A double-bit error (DBE) in the GPU's High Bandwidth Memory is an ECC uncorrectable error: unlike single-bit errors (SBE), which ECC hardware corrects transparently in-flight, a DBE means the data at that address is corrupt and cannot be reconstructed. The driver poisons the affected page and any workload touching it receives a memory fault. The GPU must be drained and reset so the driver can retire the failing memory row; a GPU that continues to log DBEs after row remapping must be retired from service.

## Affected products

- Dell PowerEdge XE9780L with 8× NVIDIA HGX B300 SXM6 GPUs (288 GB HBM3E per GPU — eight 12-high stacks of 36 GB, 8 TB/s peak bandwidth)
- NVIDIA data center driver branch R570 or later (the minimum for Blackwell Ultra); row remapping has been standard since the Ampere architecture, so it is always available on B300, which additionally supports HBM channel repair for faults a row remap cannot cover

## Error signature

The canonical signatures for this fault are:

- `ECC uncorrectable error`
- `DCGM_FI_DEV_ECC_DBE_VOL_TOTAL`

Kernel ring buffer:

```
NVRM: GPU-60ded90b: ECC DBE (double-bit error) in HBM at row 0x3A4C, bank 3
```

iDRAC Lifecycle Log message ID: `OEM.1.0.MemUCE` (severity Critical). DCGM field `DCGM_FI_DEV_ECC_DBE_VOL_TOTAL` (volatile DBE count since last reset) becomes non-zero.

## Symptoms

- iDRAC Lifecycle Log records `OEM.1.0.MemUCE` with severity Critical
- DCGM metric `DCGM_FI_DEV_ECC_DBE_VOL_TOTAL` exceeds 0 on the affected GPU
- Kernel log reports `ECC DBE (double-bit error) in HBM` with the failing row and bank
- GPU workloads on the device crash with `CUDA_ERROR_ECC_UNCORRECTABLE`, SIGBUS, or corrupted-result detection in framework-level checks
- A rising SBE rate frequently precedes the DBE by seconds to minutes (`DCGM_FI_DEV_ECC_SBE_VOL_TOTAL` trending up) — this is the strongest early-warning signal
- Scheduler marks the GPU unschedulable once the device plugin observes the fault

## Sample log excerpt

Representative sequence from a production occurrence on `gpu-server-01` (note the SBE ramp preceding the DBE):

```
14:08:00Z INFO  nvidia-smi[1235]: GPU 1: ECC SBE vol 3, DBE vol 0 — within tolerance
14:09:11Z WARN  dcgm[1234]: GPU 1: DCGM_FI_DEV_ECC_SBE_VOL_TOTAL rising: 14 correctable errors in last 60s
14:09:45Z CRIT  dcgm[1234]: GPU 1: DCGM_FI_DEV_ECC_DBE_VOL_TOTAL incremented — uncorrectable ECC error detected on HBM bank 3
14:09:45Z CRIT  kernel[  904.223191]: NVRM: GPU-60ded90b: ECC DBE (double-bit error) in HBM at row 0x3A4C, bank 3
14:09:46Z ERROR iDRAC[LifecycleLog]: OEM.1.0.MemUCE — GPU 1 HBM uncorrectable ECC error (DBE). Severity: Critical.
14:09:47Z WARN  nvidia-smi[1235]: GPU 1: ECC DBE vol 1 — threshold exceeded, marking GPU for retirement
14:09:47Z WARN  scheduler[5678]: GPU 1 on gpu-server-01 flagged for memory fault; draining workload
14:09:48Z INFO  kubelet[9012]: gpu-server-01: GPU 1 marked unschedulable — ECC fault
```

## Impact

- **Workload impact:** The process holding the poisoned page is terminated immediately; its output since the last checkpoint must be treated as suspect. Remediation drains the full node, so all jobs on the node are checkpointed and migrated. Jobs pinned to the affected GPU restart from their last checkpoint.
- **Service risk:** One node out of the pool during remediation (~15 minutes). If DBEs recur after row remapping, the GPU must be retired — a longer maintenance action with the node running at 7/8 capacity until Dell dispatch completes.
- **Data risk:** Results computed on the affected GPU between the first DBE and job termination are potentially corrupt. Flag the affected job IDs for output validation.
- **Estimated remediation duration:** ~15 minutes for the reset path.

## Root cause

1. **Aging or defective HBM cells** — the dominant cause of *recurring* DBEs. The SBE→DBE progression in the log excerpt above is the classic wear signature.
2. **Cosmic ray / particle-induced soft error** — random single occurrence with no preceding SBE trend; does not recur on the same row.
3. **Sustained high junction temperature** accelerating cell degradation (correlate with thermal history — see [KB001213](KB001213.md)).

Decision rule: one isolated DBE with a clean remap and clean diagnostics is treated as a soft error and returned to service. A second DBE on the same GPU, or any DBE with `remapping failure occurred` in `nvidia-smi -q`, is a hardware dispatch.

## Remediation steps

### Step 1 — Cordon and drain affected node (`drain_node`)

```bash
kubectl cordon gpu-server-01
kubectl drain gpu-server-01 --ignore-daemonsets --delete-emptydir-data --timeout=600s
```

Record the job IDs that were running on the affected GPU at fault time — their recent output needs validation regardless of remediation outcome.

### Step 2 — Reset GPU ECC counters and clear fault (`ecc_reset`)

A GPU reset clears the volatile ECC counters and triggers row remapping of the failing address (B300 remaps automatically on reset; no manual page retirement is needed):

```bash
nvidia-smi --gpu-reset -i <gpu_index>
```

If the driver-level reset fails (device busy or in a fault state), power cycle via iDRAC instead: `racadm serveraction powercycle`.

After reset, confirm ECC is enabled and inspect the remapping state:

```bash
nvidia-smi --query-gpu=index,ecc.mode.current --format=csv          # expect Enabled
nvidia-smi -i <gpu_index> -q | grep -A6 "Remapped Rows"
```

Healthy outcome: `Remapped Rows: Uncorrectable Error: 1`, `Remapping Pending: No`, `Remapping Failure Occurred: No`. A pending remap requires one more reset; a remapping failure means the row-remap spare pool is exhausted — escalate immediately.

### Step 3 — Re-run DCGM ECC diagnostic (`verify_health`)

Run the extended diagnostic, which includes a targeted memory stress test:

```bash
dcgmi diag -r 3
dcgmi health -g 0 -s m       # enable memory health watch
```

All tests must pass and `DCGM_FI_DEV_ECC_DBE_VOL_TOTAL` must remain 0 through the diagnostic. Then uncordon and keep the memory health watch active:

```bash
kubectl uncordon gpu-server-01
```

If the volatile DBE count increments again under workload, do not reset a second time — retire the GPU and escalate.

## Escalation

Open a Dell hardware support case (GPU replacement) if any of the following hold:

- A second DBE occurs on the same GPU after remapping
- `nvidia-smi -q` reports `Remapping Failure Occurred: Yes` or a growing remapped-row count
- The `dcgmi diag -r 3` memory test fails post-reset

Attach the DCGM diagnostic output, `nvidia-smi -q` for the affected GPU (including the Remapped Rows section), the iDRAC Lifecycle Log export, and the aggregate ECC counters (`DCGM_FI_DEV_ECC_DBE_AGG_TOTAL`), which persist across resets and establish the device's lifetime error history.
