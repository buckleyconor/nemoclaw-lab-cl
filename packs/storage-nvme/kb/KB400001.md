# NVMe Media and Data Integrity Errors — Detection and Drive Replacement

| | |
|---|---|
| **Article ID** | KB400001 |
| **Version** | 3 |
| **Last updated** | 2025-07-30 |
| **Classification** | Break/Fix — Storage Hardware |
| **Default severity** | Critical (Sev 2 — redundancy holds; Sev 1 if array already degraded) |
| **Audience** | Storage operations, datacenter operations |
| **Applies to** | Dell PowerEdge NVMe drive trays (U.2/E3.S), enterprise NVMe SSDs, RAID/erasure-coded volumes |

## Summary

An NVMe drive raising critical warning bit 0x04 (`media and data integrity errors`) is reporting that it has encountered unrecoverable media errors — reads that failed the drive's internal ECC and could not be recovered. The SMART counter `Media and Data Integrity Errors` counts these events; a non-zero, rising value means the NAND is degrading faster than the drive's spare blocks and internal remapping can absorb. Data on redundant volumes remains intact — the array reconstructs failed reads from parity/mirror — but the drive is on a failure trajectory and must be replaced promptly: the dangerous window is a second failure in the same redundancy span while the array is rebuilding. Treat a rising media-error count as a failed drive even if the drive still responds.

## Affected products

- Dell PowerEdge server NVMe backplanes and E3.S/U.2 drive trays (hot-swap capable)
- Enterprise NVMe SSDs in RAID 5/6/10 or erasure-coded software-defined storage volumes

## Error signature

The canonical signatures for this fault are:

- `media error`
- `NVMe critical warning`

`nvme smart-log` output:

```
critical_warning              : 0x4   (media and data integrity errors)
media_errors                  : 118
num_err_log_entries           : 42
```

Kernel: `blk_update_request: critical medium error, dev nvme3n1, sector 812345672` with `nvme3n1: Unrecovered Read Error`.

## Symptoms

- SMART critical warning field shows bit 0x04 set; `media_errors` counter non-zero and rising across polls
- Kernel log records `critical medium error` entries against the device on read
- iDRAC/backplane flags the slot: amber drive LED, `STO.1.0.MediaError` event raised
- Array/volume manager reports the member degraded or begins proactive rebuild onto a spare
- Latency spikes on the affected drive as its firmware retries reads (visible before the first hard error in most cases)
- The drive's error log (`nvme error-log`) accumulates entries with status `Unrecovered Read Error`

03:41:07Z WARN  storage[2001]: nvme3n1 SMART poll: media_errors 37 (was 0) — NAND degradation detected

## Impact

- **Workload impact:** None for reads and writes — the array serves affected reads from redundancy. Expect elevated latency during the rebuild window while parity/mirror data is reconstructed, proportional to rebuild priority settings.
- **Service risk:** Redundancy is degraded from the first unrecovered error until the rebuild onto the replacement/spare completes. A second drive failure in the same redundancy span during that window risks data loss — this is what makes replacement time-sensitive rather than next-maintenance-window work.
- **Data risk:** None yet on redundant volumes; verify the volume was actually redundant (Step 1) before assuming this. On any non-redundant volume a media error is data loss — identify affected files from the LBA range and restore from backup.
- **Estimated remediation duration:** ~15 minutes hands-on; rebuild typically 1–4 hours depending on drive capacity, array load, and rebuild priority.

## Root cause

1. **NAND wear-out** — the expected end-of-life mode; correlate with `percentage_used` in the SMART log. High `percentage_used` plus rising media errors is a worn drive, full stop.
2. **Premature NAND defect** — media errors at low `percentage_used`; still a replacement, but flag the drive model/firmware batch in fleet tracking to catch a bad lot.
3. **Firmware defect** — some drive firmware revisions miscount or mishandle media errors; check the drive's firmware against the vendor's advisory list before condemning a batch.
4. **Thermal excursion history** — sustained operation above the drive's rated temperature accelerates NAND wear; check the SMART temperature and the tray's thermal history if multiple drives in one tray degrade together.

## Remediation steps

### Step 1 — Identify failed NVMe drive by serial number and slot (`identify_failed_drive`)

Positively identify the physical drive before anyone touches the tray — pulling the wrong member of a degraded array is the classic self-inflicted data-loss event:

```bash
nvme smart-log /dev/nvme3n1                    # confirm critical_warning 0x4, media_errors count
nvme id-ctrl /dev/nvme3n1 | grep -i "sn\|mn"   # serial + model — match against the slot map
nvme error-log /dev/nvme3n1 | head -40
```

Cross-check the serial against the backplane slot (iDRAC → Storage → Physical Disks, or the storage manager's slot map) and blink the drive LED to confirm:

```bash
# iDRAC / storage manager: initiate locate/blink on slot 4, verify it is the amber-flagged drive
```

Also confirm the volume state: redundant and rebuild-capable (hot-spare present or replacement in hand) before proceeding.

### Step 2 — Hot-swap replacement NVMe drive (`hot_swap_drive`)

NVMe hot-swap on PowerEdge backplanes is orderly-removal, not yank-and-replace:

1. If the array manager hasn't already failed the member out, mark it offline/removed in the manager first.
2. Prepare the OS for removal (namespace/controller detach per the platform's hot-plug procedure), then remove the drive with the LED-confirmed slot.
3. Insert the replacement (equal or larger capacity, approved model/firmware), and confirm the OS enumerates it (`nvme list`) and the backplane shows it healthy.
4. Add it to the array as the rebuild target if a hot-spare didn't already take that role — in that case the new drive becomes the spare.

Record the failed drive's serial, `smart-log`, and `error-log` output in the ticket before it leaves the site — that is the warranty evidence.

### Step 3 — Confirm array rebuild completes and volume returns to optimal (`verify_rebuild`)

```bash
# Software RAID example — use the platform's equivalent for HW RAID / SDS
cat /proc/mdstat                         # rebuild progress and ETA
nvme smart-log /dev/nvme3n1              # replacement drive: critical_warning 0x0, media_errors 0
```

Monitor to completion: the volume must return to optimal/clean state, and the replacement drive's SMART must stay clean through the rebuild (a rebuild is itself a heavy read test of every other member — a second marginal drive often surfaces here). After completion, re-run a SMART poll across all tray members and close the incident only if all are clean.

## Escalation

- A second drive in the same span shows media errors or fails during rebuild → stop, treat as Sev 1, and engage storage engineering before any further drive operations; consider backup verification.
- Multiple drives of the same model/firmware degrading across trays → escalate as a batch/firmware issue with the drive vendor via Dell support; check the firmware advisory list.
- Replacement drive shows errors immediately → suspect backplane/slot (connector, signal integrity) rather than the drive; open a Dell case for the tray with both drives' logs attached.
