# Triton Model Load Failure on Jetson Edge Nodes — Detection and Remediation

| | |
|---|---|
| **Article ID** | KB300001 |
| **Version** | 3 |
| **Last updated** | 2025-08-06 |
| **Classification** | Break/Fix — Inference Serving |
| **Default severity** | Warning (Sev 3; Sev 2 if the model has no other serving node) |
| **Audience** | Edge fleet operations, ML platform |
| **Applies to** | NVIDIA Jetson AGX Orin nodes, Triton Inference Server 23.xx+ (JetPack 5.x/6.x) |

## Summary

A Triton model load failure means the server started (or polled its repository) but could not bring a model to the READY state. Triton marks the model UNAVAILABLE, keeps serving its other models, and returns errors for inference requests targeting the failed one. On Jetson edge nodes the dominant causes are artifact problems (missing/corrupt files after an incomplete model sync, TensorRT engine built for a different JetPack/TensorRT version) and resource exhaustion (the model doesn't fit in the Orin's unified memory alongside what's already loaded). The failure is confined to the model — the node and the rest of the serving stack stay healthy — so remediation is about restoring a valid artifact and confirming the model actually serves again.

## Affected products

- NVIDIA Jetson AGX Orin 32/64 GB edge nodes running Triton Inference Server (standalone or containerised via `nvcr.io` L4T images)
- All backend types; TensorRT-backend models are disproportionately affected because engine files are device- and version-specific

## Error signature

The canonical signatures for this fault are:

- `model load failure`
- `Triton failed to load`

Triton server log:

```
E0512 07:02:14 model_lifecycle.cc:596] failed to load 'resnet50' version 1:
Internal: unable to create TensorRT engine
error: creation of load-failed model 'resnet50' — model load failure
```

`GET /v2/health/ready` stays 200 (server healthy) while `GET /v2/models/resnet50/ready` returns 400 — that split is the fingerprint of a per-model load failure rather than a server crash.

## Symptoms

- Triton log shows `failed to load '<model>' version <n>` with a backend-specific reason; the model appears as `UNAVAILABLE` in the repository index (`GET /v2/repository/index`)
- Inference requests to the model fail with `Request for unknown model` or 503-class errors; other models on the node keep serving
- With TensorRT backend: `unable to create TensorRT engine`, `plan file is not compatible with this version of TensorRT`, or a deserialization error — version-mismatch signatures
- With resource exhaustion: `CUDA out of memory` or allocation failures in the load log, often after a new model was added to the repository
- Fleet dashboards show the node healthy but the model's request success rate at zero on that node

## Sample log excerpt

Representative sequence from `jetson-01` (AGX Orin 32 GB) after a model repository sync delivered an incompatible TensorRT engine:

```
07:02:10Z INFO  triton[1001]: Poll model repository /models — change detected for 'resnet50'
07:02:10Z INFO  triton[1001]: loading: resnet50:1
07:02:12Z INFO  triton[1001]: TensorRT backend: deserializing engine /models/resnet50/1/model.plan
07:02:14Z ERROR triton[1001]: model.plan deserialization failed: The engine plan file is not compatible with this version of TensorRT (built with 8.5.2, running 8.6.2)
07:02:14Z ERROR triton[1001]: failed to load 'resnet50' version 1: Internal: unable to create TensorRT engine
07:02:14Z WARN  triton[1001]: Triton failed to load model 'resnet50' version 1 — model unavailable for inference
07:02:14Z WARN  triton[1001]: model load failure: 'resnet50' marked UNAVAILABLE in model repository index
07:02:15Z INFO  triton[1001]: server remains READY — 3 of 4 models serving (yolov8, bert-base, whisper-small)
07:02:20Z WARN  edge-agent[440]: jetson-01: inference requests for 'resnet50' failing — routing to fallback node jetson-02
```

The version pair in the deserialization error tells you the fix directly: the engine was built against a different TensorRT than the node runs.

## Impact

- **Workload impact:** Inference requests for the affected model fail on this node until remediation; if the fleet has another node serving the model, clients fail over with added latency. Other models on the node keep serving through diagnosis and blip only briefly during the Triton restart in Step 2.
- **Service risk:** Low when the model is multi-homed — capacity for that model is reduced by one node. If this is the only node serving the model, that inference service is down; treat as Sev 2 and prioritise.
- **Data risk:** None — requests fail visibly; no silent corruption.
- **Estimated remediation duration:** ~10 minutes for repository fix and restart; add engine rebuild time (minutes to tens of minutes on Orin) if the TensorRT plan must be regenerated on-device.

## Root cause

1. **TensorRT/JetPack version mismatch** — the `.plan` engine was built on a different TensorRT version (or different device class) than the node runs. Engines are not portable across versions or GPU architectures; the most common cause after fleet JetPack upgrades.
2. **Incomplete or corrupt model sync** — truncated download, missing `config.pbtxt`, or a partially written version directory from an interrupted repository sync.
3. **Resource exhaustion** — the model plus already-loaded models exceed the Orin's unified memory; load fails with CUDA allocation errors, typically right after a new model was added to the node's repository.
4. **Config error** — `config.pbtxt` mismatch (wrong tensor names/dims/backend) after a model was re-exported; the backend rejects the model at load.

## Remediation steps

### Step 1 — Verify model repository path and file integrity (`check_model_repo`)

```bash
# What does Triton think is there?
curl -s localhost:8000/v2/repository/index | jq .

# Expected layout: /models/resnet50/config.pbtxt and /models/resnet50/1/model.plan
ls -lR /models/resnet50/

# Integrity: compare against the artifact registry's checksum
sha256sum /models/resnet50/1/model.plan
```

Read the load error in the Triton log — it names the failing stage. For a version-mismatch or corrupt artifact, re-pull the correct engine for this node's JetPack/TensorRT (`dpkg -l | grep -i tensorrt` to confirm the node's version) or rebuild the engine on-device with `trtexec`. For a memory failure, check what else is loaded (`curl -s localhost:8000/v2/repository/index`) against the Orin's memory (`tegrastats`) and reduce instance counts or unload a model.

### Step 2 — Restart Triton Inference Server service (`restart_triton`)

After the repository is corrected, restart to force a clean reload (explicit-mode repositories also accept a per-model load API call, but a restart guarantees no stale backend state):

```bash
sudo systemctl restart tritonserver
# or, containerised:
docker restart triton

journalctl -u tritonserver --since "-2 min" | grep -i "resnet50\|error"
```

Watch the startup log: every model in the repository should log `successfully loaded`.

### Step 3 — Confirm model reports READY and serves a test inference (`verify_model_ready`)

READY state alone doesn't prove the model computes — send a real request:

```bash
curl -s -o /dev/null -w "%{http_code}\n" localhost:8000/v2/models/resnet50/ready   # expect 200
curl -s localhost:8000/v2/models/resnet50/stats | jq '.model_stats[0].inference_stats.success'

# Test inference with a known input (perf_analyzer ships with Triton clients)
perf_analyzer -m resnet50 -u localhost:8001 -i grpc --measurement-requests 50
```

A successful perf_analyzer run with sane latency closes the incident. Re-enable the node for this model in the fleet router if it was drained.

## Escalation

- Engine rebuilt for the correct TensorRT version but load still fails → capture the full Triton log (`--log-verbose=1`) and escalate to the ML platform team; likely a model-export problem upstream, not a node problem.
- Load fails with memory errors even with the standard model set → check for memory growth in co-resident services (`tegrastats` history); if the node's model assignment simply outgrew the 32 GB Orin, escalate to capacity planning rather than restarting in a loop.
- The same model fails across many nodes after a repository sync → stop the rollout and escalate to the artifact pipeline owner; per-node remediation is the wrong tool for a bad artifact push.
