# ATM Host Communication Loss: ISO 8583 Session Down on Off-Premise ATM

| | |
|---|---|
| **Article ID** | KB800003 |
| **Version** | 4 |
| **Last updated** | 2026-01-19 |
| **Classification** | Break/Fix — Network / Host Connectivity |
| **Default severity** | Critical (Sev 1 — ATM fully out of service, no on-site staff at off-premise locations) |
| **Audience** | Network operations, ATM fleet management, field service |
| **Applies to** | All ATMs communicating with the transaction host over ISO 8583, primary VPN/WAN link with LTE backup configuration |

## Summary

ATMs communicate with the transaction switch/host using ISO 8583-based messaging (NCR's NDC and Diebold's protocols are both built on this framework) over a VPN tunnel to the institution's network, typically riding a primary WAN link with an LTE backup for resilience. When the primary link fails — a carrier outage, a site router fault, or physical WAN infrastructure issue — the VPN tunnel's keepalive signal is missed, and once a threshold number of consecutive keepalives are missed, the ATM declares the host session down and suspends all transaction types. Unlike a single-function fault (dispenser, card reader), a host communication loss takes the entire ATM out of service, since every transaction type — withdrawal, deposit, inquiry, transfer — requires a live session with the host to authorize. This is especially operationally significant at off-premise locations with no on-site staff, where there is no local recovery option and the site depends entirely on remote remediation or a truck roll.

## Affected products

- All ATM platforms using ISO 8583-based host messaging (NCR NDC, Diebold Nixdorf protocols)
- Sites configured with primary WAN + LTE backup link architecture
- Particularly relevant to off-premise / unattended locations

## Error signature

The canonical signatures for this fault are:

- `Host communication loss`
- `ISO 8583 session down`
- `ATM offline`

ATM WAN/host session log:

```
CRIT  iso8583[atm-06]: Host communication loss — ISO 8583 session down, ATM offline
CRIT  iso8583[atm-06]: All transaction types suspended — withdrawal, deposit, inquiry, transfer
```

## Symptoms

- VPN tunnel keepalive missed for multiple consecutive intervals before the session is declared down — an early warning window, not an instantaneous failure
- Primary WAN link shows no response from the provider gateway, 100% packet loss
- ISO 8583 host session drops, and the ATM suspends every transaction type simultaneously — the defining differential from a single-component fault (dispenser, reader) which suspends only that function
- Customer-facing screen shows "Out of Service"
- LTE backup link remains in standby, not yet activated, until failover is triggered
- Alert routes to network operations specifically flagged for off-premise sites without on-site staff — recovery depends entirely on remote action or dispatch

## Sample log excerpt

Representative sequence from `atm-06` (off-premise, grocery plaza location):

```
19:02:00Z INFO  wan[atm-06]: VPN tunnel active — primary WAN link, keepalive nominal
19:47:31Z WARN  wan[atm-06]: VPN tunnel keepalive missed — 1 consecutive interval
19:49:46Z WARN  wan[atm-06]: VPN tunnel keepalive missed — 2 consecutive intervals, primary WAN link degraded
19:52:01Z WARN  wan[atm-06]: VPN tunnel keepalive missed — 3 consecutive intervals, primary WAN link degraded
19:52:01Z WARN  wan[atm-06]: Primary WAN link — no response from provider gateway, packet loss 100%
19:52:18Z CRIT  iso8583[atm-06]: Host communication loss — ISO 8583 session down, ATM offline
19:52:18Z CRIT  iso8583[atm-06]: All transaction types suspended — withdrawal, deposit, inquiry, transfer
19:52:20Z WARN  wan[atm-06]: LTE backup link — standby, not yet activated
```

The three missed keepalives over roughly 5 minutes before the session is declared down give a short but real window — if remote monitoring catches the first missed keepalive, remediation can sometimes start before the ATM fully drops to out-of-service.

## Impact

- **Workload impact:** The ATM is completely out of service — no withdrawals, deposits, balance inquiries, or transfers — for the full duration of the outage, since every transaction type requires a live host session.
- **Service risk:** Medium to high depending on site traffic and staffing. Off-premise ATMs without on-site staff have no local recovery option; extended outages at high-traffic off-premise locations have direct revenue impact (surcharge/interchange revenue lost) and customer-experience impact beyond the technical fault itself.
- **Estimated remediation duration:** ~10 minutes for a remote power-cycle and link recovery. LTE failover, once triggered, is near-immediate if the backup link is provisioned and healthy — this is the primary reason backup links exist at off-premise sites.

## Root cause

In observed order of frequency:

1. **Carrier/provider-side WAN outage** — an issue upstream of the site (regional outage, provider maintenance, fiber cut) that a local power-cycle will not resolve, distinguishable when other sites on the same provider/circuit report simultaneous issues.
2. **Site router or VPN endpoint fault** — a hung or crashed router/VPN device that a power-cycle typically resolves; the most common single-site cause and the reason Step 1 is a power-cycle rather than a diagnostic-first approach.
3. **Physical WAN connectivity issue at the site** — a damaged cable, disconnected line, or local infrastructure fault (more common at off-premise sites sharing infrastructure with the host business, e.g. a grocery plaza's network closet).
4. **VPN certificate/credential expiration** — less common, but distinguishable when the fault doesn't resolve with a power-cycle and other sites on the same VPN concentrator are unaffected, pointing at a per-site credential issue rather than a link issue.

## Remediation steps

### Step 1 — Remotely power-cycle the site router/VPN endpoint (`remote_power_cycle_router`)

Attempt first — resolves the most common single-site cause without a truck roll:

```
Smart PDU / remote power management platform: select site power outlet for router/VPN endpoint
Issue power-cycle command — off for 15 seconds, then on
Monitor for VPN tunnel re-establishment and keepalive resumption over the following 2-3 minutes
```

### Step 2 — Fail over to LTE backup link if primary WAN does not recover (`failover_lte_backup`)

If the power-cycle doesn't restore the primary link within a few minutes, don't wait further before restoring service via backup:

```
Network management platform: trigger LTE failover for ATM-06
Confirm LTE link establishes VPN tunnel and keepalive
Confirm ATM transitions off OUT_OF_SERVICE status once the backup session is live
```

Restoring service on LTE backup doesn't diagnose the primary link — continue investigating the primary WAN fault in parallel or as a follow-up, since LTE is backup capacity, not a permanent replacement (typically lower bandwidth, may carry per-MB cost depending on carrier plan).

### Step 3 — Verify ATM completes ISO 8583 sign-on with the host (`verify_host_signon`)

```
Confirm ATM-06 completes a full sign-on message exchange with the host over the recovered link (primary or LTE)
Check for any sign-on rejection or partial-session state — a link that's physically up but failing sign-on indicates a separate credential/configuration issue, not just connectivity
```

### Step 4 — Confirm a test transaction completes successfully (`confirm_test_transaction`)

```
Initiate a balance inquiry or small test transaction (per fleet test-transaction procedure) before releasing the ATM to full customer service
Confirm full round-trip: request, host authorization, response displayed correctly
```

Do not release the ATM to service on sign-on success alone — a link that signs on but drops under real transaction load has happened before and is only caught by an actual transaction test.

## Escalation

- Primary WAN link does not recover within 30 minutes of power-cycle, and other sites on the same provider circuit report similar issues → escalate to the WAN provider directly; this is a carrier-side outage, not resolvable by site-level remote action.
- LTE failover also fails to establish a session → escalate immediately to network operations as a dual-link failure; this is a higher-priority incident than a single-link outage and may require emergency field dispatch given the site has zero connectivity options remaining.
- Site remains on LTE backup beyond 24 hours without primary link recovery → escalate to field service for physical site visit; extended backup-link operation both costs more (per-MB LTE charges) and removes the site's own resilience if LTE also degrades.
