# MPI Process Crash in Slurm Batch Jobs — Triage, Requeue, and Node Health

| | |
|---|---|
| **Article ID** | KB500001 |
| **Version** | 3 |
| **Last updated** | 2025-06-25 |
| **Classification** | Break/Fix — HPC Workload / Node |
| **Default severity** | Warning (Sev 3; Sev 2 if the same node kills multiple distinct jobs) |
| **Audience** | HPC operations, research computing support |
| **Applies to** | Slurm 22.05+ with OpenMPI 4.x / MPICH, RHEL/Rocky 9 compute nodes |

## Summary

When one MPI rank dies — segfault, signal, or unhandled exception — the MPI runtime tears down every rank in the job and Slurm records the job as failed. The visible event ("job 48213 crashed on hpc-node-01") therefore conflates two very different problems: an **application fault** (bug, bad input, out-of-bounds access), which is the common case and belongs to the job owner, and a **node fault** (failing DIMM, degraded interconnect, kernel issue), which is rarer but poisons every job scheduled onto that node. The operational job is to preserve the crash evidence, get the user's work requeued from checkpoint, and make the application-vs-node determination before the node takes its next job — a crashing node in the queue is a job-killing machine on a loop.

## Affected products

- HPC compute nodes under Slurm with OpenMPI (`mpirun`/`srun`-launched jobs); guidance applies equally to MPICH/Intel MPI with different message text
- Checkpointing and non-checkpointing workloads (the requeue step differs)

## Error signature

The canonical signatures for this fault are:

- `MPI process crash`
- `terminated abnormally`

OpenMPI teardown message:

```
mpirun noticed that process rank 0 with PID 71442 on node hpc-node-01
exited on signal 11 (Segmentation fault).
MPI process rank 0 terminated abnormally — all ranks torn down
```

Slurm: job state `FAILED`, `DerivedExitCode` non-zero; `slurmd` on the node logs the step termination signal.

## Symptoms

- Slurm job ends in `FAILED` state; `sacct -j <jobid>` shows a signal-based exit (e.g. `0:11` for SIGSEGV) on one step
- OpenMPI reports the failing rank, PID, node, and signal, then tears down remaining ranks (`terminated abnormally`)
- A core dump appears in the configured crash path (`/var/crash` or the job's working directory, per `core_pattern`)
- Other ranks' logs end mid-iteration without errors of their own — they were killed by the teardown, not by faults; only the first-failing rank matters for diagnosis
- Node-fault indicators when present: `mce` / EDAC memory errors in the node's kernel log near the crash time, interconnect errors, or multiple *different* applications crashing on the same node

## Sample log excerpt

Representative sequence for Slurm job 48213 (64 ranks across 4 nodes) with rank 0 on `hpc-node-01` segfaulting mid-run:

```
11:20:03Z INFO  slurmd[hpc-node-01]: Launching job step 48213.0 — 16 ranks local, job total 64
11:47:26Z INFO  app[71442]: [rank 0] iteration 18400/50000 — residual 3.1e-7, checkpoint written it=18000
11:52:41Z CRIT  kernel[hpc-node-01]: app[71442]: segfault at 7f2a4c001018 ip 00000000004a2d17 sp 00007ffd23e1a930 error 4 in app[400000+2ff000]
11:52:41Z WARN  slurmd[hpc-node-01]: task 0 of job step 48213.0 exited on signal 11
11:52:41Z CRIT  mpirun[71400]: mpirun noticed that process rank 0 with PID 71442 on node hpc-node-01 exited on signal 11 (Segmentation fault)
11:52:41Z WARN  mpirun[71400]: MPI process crash: rank 0 (hpc-node-01) terminated abnormally on signal 11 (Segmentation fault)
11:52:42Z WARN  mpirun[71400]: tearing down remaining 63 ranks — job cannot continue with a failed rank
11:52:43Z INFO  slurmctld[head]: Job 48213 (user rsmith, account chem-dft) completed, state FAILED, exit 0:11
11:52:43Z INFO  slurmd[hpc-node-01]: core dump written: /var/crash/core.app.71442.hpc-node-01.1718021561
11:52:45Z INFO  node-health[880]: hpc-node-01: post-job check queued — 1 job failure recorded (0 prior in 7 days)
```

The kernel `segfault` line placing the fault inside the application's own text segment (`in app[...]`) — with no memory/MCE errors in the same window — points at an application bug rather than the node.

## Impact

- **Workload impact:** The job loses compute time back to its last checkpoint (here ~2,900 iterations); a non-checkpointing job loses its full elapsed runtime. Other jobs sharing the node are unaffected unless the health check in Step 3 fails.
- **Service risk:** Low for a single crash — statistically an application fault. The risk to manage is the recurring-node case: a node with a hardware fault will keep killing multi-node jobs, multiplying lost core-hours, so the health-check gate before requeue matters more than the requeue itself.
- **Data risk:** Output written after the last checkpoint may be incomplete/corrupt; advise the owner to restart from the checkpoint, not from partial output files.
- **Estimated remediation duration:** ~10 minutes for evidence collection and requeue; restart time depends on scheduler backfill.

## Root cause

1. **Application bug** — the dominant cause: out-of-bounds access, race, or unhandled edge case in the input data. Fingerprint: crash in the application's own code (as in the excerpt), reproducible at the same iteration/input, no node-level errors.
2. **Bad input / configuration** — a malformed input deck or an MPI decomposition that only breaks at a specific rank count; crashes early and deterministically.
3. **Node memory fault** — correctable-error storms or an uncorrectable DIMM error killing whatever process is on the bad page; fingerprint: EDAC/MCE kernel entries, different applications crashing on the same node, crashes at random points.
4. **Interconnect/fabric fault** — rank failures presenting as transport errors or hangs before the crash; check fabric counters when the MPI error text mentions communication rather than a signal.
5. **Resource exhaustion** — OOM-killer terminating a rank (visible in the node's kernel log as `Out of memory: Killed process`); an application-sizing issue, but reported as an abnormal termination.

## Remediation steps

### Step 1 — Collect core dump and job logs from /var/crash (`collect_core_dump`)

Preserve evidence before the scratch space or crash directory is recycled:

```bash
JOBID=48213; NODE=hpc-node-01
mkdir -p /shared/incidents/$JOBID
cp /var/crash/core.app.71442.* /shared/incidents/$JOBID/
sacct -j $JOBID --format=JobID,State,ExitCode,NodeList,Elapsed,MaxRSS > /shared/incidents/$JOBID/sacct.txt
cp <job stdout/stderr files> /shared/incidents/$JOBID/
journalctl -k --since "11:45" --until "11:55" -D /var/log/journal --no-pager > /shared/incidents/$JOBID/kernel.log   # run on $NODE
```

Get a first-pass backtrace while the environment still matches the binary:

```bash
gdb -batch -ex bt /path/to/app /shared/incidents/$JOBID/core.app.71442.* | head -30
```

A backtrace inside application code → route to the job owner with the incident directory. MCE/EDAC entries in the kernel log → treat as a node fault and prioritise Step 3.

### Step 2 — Requeue the failed MPI job via Slurm (`requeue_job`)

Confirm with the owner (or their standing policy) that the job restarts from its checkpoint, then:

```bash
scontrol requeue $JOBID          # if the job script is requeue-safe (reads its own checkpoint)
# or resubmit explicitly:
sbatch --dependency=singleton job_48213.sh
```

If the evidence points at the node, exclude it so the restart doesn't land on the same machine:

```bash
sbatch --exclude=hpc-node-01 job_48213.sh
```

For non-checkpointing jobs, warn the owner the run restarts from zero — worth stating explicitly before burning the core-hours.

### Step 3 — Run node health check before returning node to the queue (`verify_node_health`)

Gate the node, don't assume it: drain, test, and only then return it to service:

```bash
scontrol update nodename=hpc-node-01 state=drain reason="post-crash health check job 48213"

# On the node: memory, then the cluster's standard health suite
sudo edac-util --status && sudo edac-util --report=full
sudo /opt/cluster/bin/node-healthcheck --full     # site NHC: CPU, memory, fabric, filesystem

scontrol update nodename=hpc-node-01 state=resume   # only on a clean pass
```

A clean pass with an application-code backtrace closes the infrastructure side of the incident (the application side belongs to the job owner). Any memory/fabric finding keeps the node drained and escalates.

## Escalation

- EDAC/MCE errors or a failed health check → keep the node drained and open a hardware case (DIMM/board) with the kernel log and health-check output; do not resume the node to clear a queue backlog.
- The same node kills 2+ *different* applications within 7 days even with clean health checks → escalate to HPC engineering for extended diagnostics (memtester soak, fabric loopback); the standard NHC misses marginal faults.
- The same application crashes across *different* nodes → application/input problem; route to the job owner or research computing support with the collected incident directory — node remediation won't help.
