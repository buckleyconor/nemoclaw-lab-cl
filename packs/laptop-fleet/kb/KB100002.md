# GPU Out of Memory: CUDA OOM on NVIDIA RTX in Dell Precision Laptops

| | |
|---|---|
| **Article ID** | KB100002 |
| **Version** | 4 |
| **Last updated** | 2025-06-11 |
| **Classification** | Break/Fix — GPU Compute / Workload |
| **Default severity** | Warning (Sev 3) |
| **Audience** | End-user computing support, AI/ML enablement |
| **Applies to** | Dell Precision 7780/7680/5680 with NVIDIA RTX Ada Generation Laptop GPUs |

## Summary

A CUDA Out of Memory (OOM) error occurs when a GPU workload requests more VRAM than the device has free. Mobile RTX Ada GPUs carry substantially less VRAM than their datacenter counterparts (RTX 5000 Ada: 16 GB; RTX 4000 Ada: 12 GB), so local LLM fine-tuning and large-batch training jobs that were sized for server GPUs hit OOM routinely. The failing allocation raises `torch.cuda.OutOfMemoryError` (or the framework equivalent); note that once an OOM or a subsequent `device-side assert` has fired, the CUDA context is poisoned — later errors in the same process are unreliable, and the process must be restarted rather than retried in place. This is a workload-sizing condition, not a hardware fault; the device needs no repair.

## Affected products

- Dell Precision 7780 / 7680 / 5680 with NVIDIA RTX Ada Generation Laptop GPUs
- PyTorch ≥ 2.0, TensorFlow ≥ 2.12, llama.cpp/CUDA inference stacks, on Windows 11 or Ubuntu 22.04

## Error signature

The canonical signatures for this fault are:

- `CUDA out of memory`
- `GPU OOM`
- `device-side assert`

Application output:

```
torch.cuda.OutOfMemoryError: CUDA out of memory. Tried to allocate 4.00 GiB
(GPU 0; 16.00 GiB total capacity; 15.90 GiB already allocated)
RuntimeError: CUDA error: device-side assert triggered
```

## Symptoms

- Application aborts with `CUDA out of memory. Tried to allocate X GiB` naming the device and current allocation
- `nvidia-smi` shows the GPU's memory at or near 100% in the seconds before the crash
- Follow-on errors in the same process: `device-side assert triggered`, `invalid device function`, or hangs — all artifacts of the poisoned context, not separate faults
- On Windows, the display compositor (`dwm.exe`) holds several hundred MB of VRAM, so the usable budget is below the nameplate figure
- Recurs deterministically at the same training step / model load, unlike hardware memory errors ([KB100003](KB100003.md)) which are random

## Impact

- **Workload impact:** The offending process is terminated to release VRAM — unsaved work in that application is lost (training progress since the last checkpoint, unsaved notebook state). Other applications on the device are unaffected.
- **Service risk:** Low — single-device action; the device remains usable throughout and no hardware is implicated. Without the workload adjustment in Step 4 the failure will recur on the next run.
- **Data risk:** None beyond the terminated process's unsaved state.
- **Estimated remediation duration:** ~5 minutes to identify, terminate, and verify; workload tuning is advisory follow-up with the user.

## Root cause

1. **Model too large for VRAM** — weights plus optimizer state plus activations exceed the 12–16 GB mobile budget (an 8B model in FP16 with Adam state does not fit in 16 GB for training).
2. **Batch size / sequence length oversized** — activation memory grows with both; jobs copied from server configurations are the usual source.
3. **VRAM already committed** — display compositor, a second notebook kernel, or a leaked process from a previous crashed run holding memory (visible in Step 1).
4. **Memory fragmentation** — long-running processes with varied allocation sizes failing a large allocation despite sufficient total free VRAM (PyTorch reports "reserved but unallocated" memory in the OOM message).

## Remediation steps

### Step 1 — List GPU processes consuming VRAM (`identify_gpu_processes`)

```bash
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv
```

Identify the highest consumer. Also check for orphaned processes from previously crashed runs — a leaked 14 GB allocation from a dead kernel is a common finding and changes the fix from "tune the workload" to "kill the leak."

### Step 2 — Terminate the highest VRAM consumer (`terminate_gpu_process`)

Confirm with the user before killing anything with unsaved state, then:

```bash
# Linux
kill <pid>            # graceful first
kill -9 <pid>         # only if it doesn't exit

# Windows (PowerShell)
Stop-Process -Id <pid> -Force
```

### Step 3 — Verify VRAM freed (`clear_gpu_memory`)

```bash
nvidia-smi --query-gpu=memory.used,memory.free --format=csv
```

`memory.free` should return to near the device total (minus ~0.5–1 GB for the display stack on the machine's internal panel). If memory remains held with no process listed, the driver has a stuck context — reboot the device; there is no user-level command that reliably reclaims it.

### Step 4 — Advise workload adjustment (`advise_batch_resize`)

For the application owner, in order of effectiveness on 12–16 GB mobile GPUs:

- Reduce `batch_size` (activation memory scales linearly; use gradient accumulation to preserve the effective batch)
- Enable gradient checkpointing: `model.gradient_checkpointing_enable()` — trades ~20% compute for a large activation-memory saving
- Quantise for inference: 8-bit or 4-bit via `bitsandbytes` (a 8B model drops from ~16 GB FP16 to ~5 GB in 4-bit)
- Offload with `accelerate` `device_map="auto"` to split layers between GPU and CPU RAM
- Set `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` where fragmentation (large "reserved but unallocated" figure) is the cause

## Escalation

OOM is workload-sizing, not a device fault — there is no hardware escalation path. If the workload cannot fit after tuning, route the request to ML infrastructure for scheduling on a higher-VRAM resource (RTX 6000 Ada 48 GB workstation, or a datacenter GPU node). Recurring fleet-wide OOM tickets from the same team indicate a training-workflow sizing problem to raise with that team's lead rather than per-device fixes.
