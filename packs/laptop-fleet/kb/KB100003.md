# GPU ECC Double-Bit Error on Mobile NVIDIA RTX — Detection and Recovery

| | |
|---|---|
| **Article ID** | KB100003 |
| **Version** | 4 |
| **Last updated** | 2025-08-27 |
| **Classification** | Break/Fix — GPU Memory Hardware |
| **Default severity** | Warning (Sev 3; Sev 2 if recurring — warranty path) |
| **Audience** | End-user computing support, fleet operations |
| **Applies to** | Dell Precision 7780/7680 with NVIDIA RTX 5000 / 4000 Ada (ECC-capable GDDR6) |

## Summary

An ECC Double-Bit Error (DBE) means the GPU detected a memory word with two or more flipped bits — beyond what ECC can correct. Unlike Single-Bit Errors (SBE), which are corrected transparently and only logged, a DBE is uncorrectable: the data at that address is lost, and any computation that read it produced unreliable results. On ECC-enabled mobile RTX GPUs the driver fails the running compute job with `uncorrectable ECC error encountered` and increments the volatile DBE counter. A single DBE can be a transient (particle-induced) event and is cleared by a reset; a DBE that recurs under workload within 24 hours indicates degrading VRAM and routes the device to warranty repair. Because the discrete GPU can be idled while the user works on integrated graphics, this fault does not take the laptop out of service.

## Affected products

- Dell Precision 7780 / 7680 with NVIDIA RTX 5000 / 4000 Ada Generation (ECC-capable GDDR6, ECC enabled via `nvidia-smi --ecc-config` or SBIOS)
- NVIDIA driver R525 or later; DCGM 3.x where fleet monitoring is deployed

## Error signature

The canonical signatures for this fault are:

- `ECC error`
- `double bit error`
- `ECC DBE`

Monitoring/driver output:

```
ECC error detected: double bit error on GPU 0 frame buffer
nvidia-smi: ECC DBE volatile count=1 on GPU 00000000:01:00.0
CUDA error: uncorrectable ECC error encountered
```

DCGM field `DCGM_FI_DEV_ECC_DBE_VOL_TOTAL` (field ID 312) > 0 on the device.

## Symptoms

- DCGM health check fails the GPU on memory: `Health check FAILED: GPU 0 — memory error (DBE)`
- `nvidia-smi --query-gpu=ecc.errors.uncorrected.volatile.total --format=csv` returns > 0
- The running compute application aborts with `CUDA error: uncorrectable ECC error encountered`
- A rising SBE count in the minutes before the DBE (visible in DCGM/nvidia-smi telemetry) — the wear signature that predicts recurrence
- Display output is unaffected — the fault surfaces only under compute workloads touching the failing region

## Sample log excerpt

Representative sequence from `laptop-03` (Precision 7780, RTX 5000 Ada, ECC enabled) during an FP16 fine-tuning run — note the SBE uptick before the DBE:

```
16:30:02Z INFO  dcgm[2200]: ECC baseline: SBE vol=0, DBE vol=0, SBE agg=0, DBE agg=0
16:33:00Z INFO  pytorch[3310]: Epoch 2 step 100/200 — loss=0.71
16:34:05Z WARN  dcgm[2200]: ECC SBE volatile count increased to 3 on GPU 0 — within threshold
16:35:22Z CRIT  dcgm[2200]: ECC error detected: double bit error on GPU 0 frame buffer
16:35:22Z CRIT  dcgm[2200]: nvidia-smi: ECC DBE volatile count=1 on GPU 00000000:01:00.0
16:35:22Z CRIT  dcgm[2200]: Health check FAILED: GPU 0 — memory error (DBE)
16:35:23Z WARN  pytorch[3310]: CUDA error: uncorrectable ECC error encountered
16:35:23Z WARN  pytorch[3310]: Training suspended — GPU memory integrity compromised
```

## Impact

- **Workload impact:** GPU-accelerated applications are closed for the reset; results computed on the affected GPU since the error must be treated as suspect and the job re-run from its last checkpoint. The user can keep working on integrated graphics throughout — no downtime for standard productivity work.
- **Service risk:** Low for a single occurrence. If DBEs persist after reset, the device is flagged for warranty replacement and the user should avoid GPU compute work on it until the repair — a scheduling inconvenience, not an outage.
- **Data risk:** Compute results derived from the corrupted memory word are unreliable; flag the affected job's recent output for validation.
- **Estimated remediation duration:** ~10 minutes (drain, diagnostics, reset, reboot, re-verify).

## Root cause

1. **Particle-induced bit flip (soft error)** — random single occurrence, no preceding SBE trend, does not repeat at the same address. The benign case; cleared by reset.
2. **Degrading VRAM cells (hardware)** — the SBE-ramp-then-DBE pattern in the excerpt above; recurs under load. Warranty repair.
3. **Thermal stress** — sustained high memory junction temperature accelerating cell wear; common in laptops run at full compute load on soft surfaces or with blocked vents. Check the device's thermal history.
4. **Power transient** — unstable DC input or a failing battery/adapter affecting the memory rail; suspect when DBEs correlate with charger swaps or docking events.

## Remediation steps

### Step 1 — Terminate active GPU compute workloads (`drain_gpu_workloads`)

Stop compute processes cleanly before diagnostics (confirm with the user; training state since the last checkpoint is already suspect):

```bash
nvidia-smi --query-compute-apps=pid,process_name --format=csv,noheader
kill <pid>    # per process; -9 only if unresponsive
```

### Step 2 — Run ECC diagnostic (`run_ecc_diagnostic`)

Capture both volatile (since boot) and aggregate (lifetime) counters — the aggregate history is what distinguishes a first event from a pattern, and is the key evidence for a warranty claim:

```bash
nvidia-smi --query-gpu=ecc.errors.corrected.volatile.total,ecc.errors.uncorrected.volatile.total,ecc.errors.corrected.aggregate.total,ecc.errors.uncorrected.aggregate.total --format=csv

# Where DCGM is deployed:
dcgmi health -g 0 -c
```

Record the output in the ticket before resetting — the volatile counters are destroyed by the reset in Step 3.

### Step 3 — Reset ECC counters and reboot (`reset_ecc_counters`)

```bash
nvidia-smi --ecc-config=1    # confirm ECC remains enabled
shutdown -r now              # reboot clears volatile counters and re-initialises VRAM
```

(A driver-level GPU reset is typically unavailable on Optimus-switched mobile GPUs, so a full reboot is the supported reset path.) After reboot, verify a clean baseline:

```bash
nvidia-smi --query-gpu=ecc.errors.uncorrected.volatile.total --format=csv,noheader   # expect 0
```

Then have the user re-run the original workload. A representative 30-minute compute soak with the volatile DBE count remaining 0 closes the incident as a transient.

### Step 4 — Raise hardware repair ticket if persistent (`escalate_if_persistent`)

If the DBE recurs within 24 hours of workload resumption, stop repeating resets — the VRAM is failing:

- Open a Dell ProSupport hardware case for GPU/system-board replacement, attaching the pre-reset counter capture from Step 2, the aggregate ECC history, and `nvidia-bug-report` output
- Advise the user to route GPU compute work elsewhere until repair; ordinary desktop use on integrated graphics is safe
- Mark the asset in fleet inventory so the sentinel treats further ECC events on it as known-faulty rather than new incidents
