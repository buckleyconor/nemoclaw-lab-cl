# Display Driver TDR: NVIDIA nvlddmkm Timeout on Dell Precision Laptops

| | |
|---|---|
| **Article ID** | KB100001 |
| **Version** | 5 |
| **Last updated** | 2025-10-02 |
| **Classification** | Break/Fix — Graphics Driver |
| **Default severity** | Critical (Sev 2 — device recovers; Sev 1 if BSOD loop) |
| **Audience** | End-user computing support, fleet operations |
| **Applies to** | Dell Precision 7780/7680/5680 (RTX Ada), 7770/7670 (RTX Ampere), Windows 11 |

## Summary

A TDR (Timeout Detection and Recovery) event occurs when the Windows GPU scheduler detects that the graphics device has not responded within the timeout window (2 seconds by default). Windows resets the display driver in place: the screen blanks briefly, the desktop returns, and Event ID 4101 (`Display driver nvlddmkm stopped responding and has successfully recovered`) is written to the System Event Log. The user session survives, but every GPU context is destroyed — CUDA applications lose their state and must reinitialise, and GPU-accelerated apps may need relaunching. If the reset itself fails, the machine blue-screens with `VIDEO_TDR_FAILURE (nvlddmkm.sys)`. A single TDR is recoverable; repeated TDRs on the same device indicate a driver regression, a power/thermal configuration problem, or failing GPU hardware.

## Affected products

- Dell Precision 7780, 7680, 5680 with NVIDIA RTX 5000 / 4000 Ada Generation Laptop GPU
- Dell Precision 7770, 7670 with NVIDIA RTX A5500 / A4500 (Ampere)
- NVIDIA driver branches R525–R546 on Windows 11 22H2/23H2

## Error signature

The canonical signatures for this fault are:

- `TDR`
- `Display driver stopped responding`
- `nvlddmkm`

Windows System Event Log:

```
Event ID: 4101   Source: nvlddmkm   Level: Error
Display driver nvlddmkm stopped responding and has successfully recovered.
```

A LiveKernelEvent 141 (hardware error) entry in Reliability Monitor and a dump under `C:\Windows\LiveKernelReports\` typically accompany the event.

## Symptoms

- Display goes black for 2–10 seconds and recovers; open windows survive but GPU-accelerated content may be blank until the app is relaunched
- Windows Event Viewer → System shows Event ID 4101, Source `nvlddmkm`
- CUDA applications running at the time fail with `CUDA error: an illegal memory access was encountered` or `device-side assert triggered` (context lost)
- `C:\Windows\LiveKernelReports\` or `C:\Windows\Minidump\` contains a new dump file timestamped at the event
- In the failure case: BSOD `VIDEO_TDR_FAILURE` naming `nvlddmkm.sys`

## Sample log excerpt

Representative sequence from `laptop-02` (Precision 7780, RTX 5000 Ada) during a CUDA training workload:

```
14:10:16Z INFO  cuda[8821]: Allocated 8192 MB VRAM for model weights
14:11:30Z INFO  cuda[8821]: Training epoch 1/50 — batch 512/1024
14:12:03Z WARN  kernel[EventLog]: GPU scheduler detected hang on \\Device\\Video0
14:12:03Z WARN  kernel[EventLog]: TDR detected: initiating recovery sequence
14:12:04Z CRIT  EventLog[System]: Display driver nvlddmkm stopped responding and has successfully recovered
14:12:04Z CRIT  EventLog[System]: Event ID 4101 — Source: nvlddmkm, Level: Error
14:12:04Z WARN  NVDisplay[1024]: LiveKernelEvent 141 logged to C:\Windows\LiveKernelReports
14:12:05Z WARN  cuda[8821]: CUDA context lost due to TDR — application must reinitialise
14:12:06Z CRIT  cuda[8821]: RuntimeError: CUDA error: an illegal memory access was encountered
```

The trigger here is the classic pattern: a long-running CUDA kernel monopolising the GPU past the 2-second scheduler deadline while the same GPU is also driving the display.

## Impact

- **Workload impact:** Brief screen flicker during driver restart; the user session is preserved. GPU-accelerated applications (browsers, CAD, ML runtimes) lose their GPU context and may need relaunching. Any CUDA job running at the time aborts and must restart — unsaved in-GPU state is lost.
- **Service risk:** Low — single-device action, no data loss expected. Recurring TDRs (3+ in 7 days) indicate a driver or hardware fault; flag the device for depot repair before it progresses to a BSOD loop.
- **Estimated remediation duration:** ~5 minutes for evidence collection and driver restart; a driver update adds ~15 minutes including reboot.

## Root cause

Common TDR triggers on Precision mobile workstations, in observed order of frequency:

1. **Driver regression** — a driver version with known shader-compiler or power-management bugs for the installed GPU. Check the current branch's release notes first.
2. **Long CUDA kernels on the display GPU** — compute kernels exceeding the 2 s scheduler deadline on a GPU that is also rendering the desktop (headless/compute-only devices don't TDR).
3. **Power limit conflicts** — battery or "Optimized" power mode reducing GPU TDP mid-kernel, stretching execution past the deadline. Strongly correlated with TDRs that occur only on battery.
4. **Thermal throttle cascade** — sustained thermal limit dropping clocks far enough that in-flight work misses the deadline.
5. **Application-level GPU hang** — DX12/Vulkan synchronisation misuse; identifiable when TDRs follow one specific application regardless of driver version.

## Remediation steps

### Step 1 — Collect TDR minidump (`collect_tdr_dump`)

Preserve the evidence before any driver change overwrites it:

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\Desktop\TDR-dumps" | Out-Null
Copy-Item "C:\Windows\Minidump\*.dmp","C:\Windows\LiveKernelReports\*.dmp" `
  -Destination "$env:USERPROFILE\Desktop\TDR-dumps" -ErrorAction SilentlyContinue
Get-WinEvent -FilterHashtable @{LogName='System'; Id=4101} -MaxEvents 10 |
  Format-List TimeCreated, Message | Out-File "$env:USERPROFILE\Desktop\TDR-dumps\tdr-events.txt"
```

The event history establishes whether this is a first occurrence or a pattern — that distinction drives everything after Step 2.

### Step 2 — Update GPU driver (`update_gpu_driver`)

Record the current version, then install the latest validated driver:

```powershell
nvidia-smi --query-gpu=driver_version --format=csv,noheader
```

Install via Dell Command | Update (preferred for fleet devices — it delivers the Dell-validated driver) or the NVIDIA Studio Driver for compute/content workloads. Avoid Game Ready drivers on Precision fleet machines. Reboot after installation.

### Step 3 — Increase TdrDelay registry value (`disable_tdr_registry`)

Only if TDRs are triggered by legitimate long CUDA kernels (Event 4101 always coincides with compute jobs) — this raises the scheduler deadline rather than fixing a fault:

```powershell
# Run as Administrator
Set-ItemProperty -Path "HKLM:\System\CurrentControlSet\Control\GraphicsDrivers" `
  -Name "TdrDelay" -Value 8 -Type DWord
Restart-Computer
```

**Note:** this is a scoped workaround, not a fix. It masks genuine device hangs for up to 8 seconds, so it must not be fleet-defaulted; apply it per-device with a ticket reference, and remove it if TDRs continue.

### Step 4 — Run stress test to confirm stability (`verify_stability`)

After the driver update and reboot, run a sustained combined graphics + compute load for at least 30 minutes — NVIDIA FrameView over a looping 3D benchmark, or a representative CUDA training job:

```powershell
# Watch clocks/thermals during the soak; a repeat TDR lands in the System log
nvidia-smi --query-gpu=temperature.gpu,clocks.sm,power.draw --format=csv -l 5
Get-WinEvent -FilterHashtable @{LogName='System'; Id=4101} -MaxEvents 3
```

Zero new 4101 events during the soak closes the incident. Verify on both AC and battery if the original events occurred on battery.

## Escalation

- TDR recurs after driver update and TdrDelay adjustment → Dell ProSupport case with the collected minidumps, the 4101 event history, and `nvidia-bug-report` output; request GPU board diagnostics / depot repair.
- BSOD `VIDEO_TDR_FAILURE` at any point → skip the workaround path and escalate directly; a failed recovery means the driver could not reset the device.
- TDRs isolated to one application across driver versions → route to the application vendor with the dump files; not a device fault.
