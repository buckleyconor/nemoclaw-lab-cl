# Fabric Link Down on Leaf-Spine Uplink — Detection and Remediation

| | |
|---|---|
| **Article ID** | KB200001 |
| **Version** | 3 |
| **Last updated** | 2025-09-12 |
| **Classification** | Break/Fix — Network Fabric |
| **Default severity** | Critical (Sev 2 — redundancy holds; Sev 1 if last uplink) |
| **Audience** | Network operations, datacenter operations |
| **Applies to** | Dell PowerSwitch S5248F-ON (leaf), Z9332F-ON (spine), SmartFabric OS10 |

## Summary

A link-down event on a leaf-to-spine uplink means the interface lost carrier: the physical layer between the leaf and its spine dropped, taking the LLDP adjacency, any BFD session, and the underlay BGP session on that link down with it. In a leaf-spine fabric the traffic impact is absorbed immediately — ECMP reroutes flows over the remaining uplinks within the BFD detection window — so the operational problem is not an outage but degraded uplink capacity and lost redundancy. The remediation goal is to restore the link (or dispatch optics/cable replacement) and confirm the fabric reconverged cleanly, before a second failure on the same leaf isolates its rack.

## Affected products

- Dell PowerSwitch S5248F-ON leaf switches and Z9332F-ON spines running SmartFabric OS10 10.5.x
- 100G QSFP28 DAC and AOC uplinks; also applies to optical links with separate transceivers and fiber

## Error signature

The canonical signatures for this fault are:

- `link down`
- `LinkDown`

OS10 syslog:

```
%Node.1-Unit.1:PRI:OS10 %log-notice:IFM_ASTATE_DN: Changed interface admin state to down :ethernet1/1/1
NET.1.0.LinkDown — Link down detected on Ethernet1/1
```

Accompanied by LLDP neighbor age-out, BFD session down, and a BGP `Idle` transition for the peer on that link.

## Symptoms

- Interface shows `down (Link down)` in `show interface status`; event `NET.1.0.LinkDown` raised with severity Critical
- LLDP neighbor on the port disappears (`show lldp neighbors` no longer lists the spine)
- BFD reports the session down within its detection multiplier (typically < 1 s); underlay BGP session to that spine moves Established → Idle
- ECMP path count to spine prefixes drops (e.g. 4 → 3 in `show ip route`)
- Interface counters may show CRC/FCS errors climbing in the minutes before the drop — the classic degrading-optics signature
- Traffic continues flowing; per-uplink utilisation on surviving links rises proportionally

## Sample log excerpt

Representative sequence from `leaf-01` (S5248F-ON) losing its Ethernet1/1 uplink to `spine-01` — note the FCS error ramp before the drop:

```
08:14:02Z INFO  switch[syslog]: leaf-01 Ethernet1/1: FCS error rate 1.1e-8 — within tolerance
08:16:45Z WARN  switch[syslog]: leaf-01 Ethernet1/1: FCS errors rising — 214 in last 60s (was 0/min baseline)
08:17:20Z WARN  switch[syslog]: leaf-01 Ethernet1/1: Rx power -13.8 dBm — below warning threshold (-12.0 dBm)
08:17:52Z CRIT  switch[syslog]: leaf-01 Ethernet1/1: link down — carrier lost
08:17:52Z CRIT  switch[syslog]: NET.1.0.LinkDown — Link down detected on Ethernet1/1 (uplink leaf-01 to spine-01)
08:17:52Z WARN  switch[bfd]: BFD session 10.0.1.0/31 to spine-01 DOWN — detection time 300ms
08:17:52Z WARN  switch[bgp]: BGP peer 10.0.0.1 (spine-01) Established -> Idle — interface down
08:17:53Z INFO  switch[route]: ECMP group to spine prefixes reduced: 4 paths -> 3. Traffic rerouted.
08:17:53Z WARN  switch[lldp]: LLDP neighbor spine-01 (Ethernet1/32) aged out on Ethernet1/1
08:18:10Z INFO  switch[syslog]: Uplink utilisation: Ethernet1/2 58%, Ethernet1/3 61%, Ethernet1/4 57% (was ~44% each)
```

The falling Rx optical power reading identifies this as a physical-layer degradation (optics or fiber), not a configuration event — there is no admin-down entry.

## Impact

- **Workload impact:** None expected — flows rerouted over the remaining ECMP uplinks within the BFD detection window. Long-lived flows that hashed onto the failed link resumed on a surviving path; a sub-second blip may also occur when the link is restored and paths rebalance.
- **Service risk:** The leaf runs with reduced spine capacity (75% in a 4-uplink design) until the link is restored, and surviving uplinks carry proportionally more traffic — check they are not approaching saturation at peak. Losing a second uplink on the same leaf compounds capacity loss; losing all of them isolates the rack.
- **Data risk:** None.
- **Estimated remediation duration:** ~10 minutes for inspection and interface bounce; add dispatch time if optics or cable must be replaced.

## Root cause

In observed order of frequency for leaf-spine uplinks:

1. **Degraded/failing optics or DAC** — falling Rx power and rising FCS errors before the drop (as in the excerpt). Replace the transceiver/cable.
2. **Physical disturbance** — cable unseated or damaged during adjacent rack work; correlate the timestamp with datacenter access records.
3. **Remote-end event** — the spine port failed or was administratively downed; check the spine's log for the same window before touching the leaf side.
4. **Transceiver seating/contamination** — dirty fiber end-face or partially seated QSFP; typically shows as flapping rather than a clean down.
5. **Switch port hardware failure** — rare; diagnosed when a known-good transceiver and cable still won't link on that port but do on a spare port.

## Remediation steps

### Step 1 — Inspect physical cable and optics on Ethernet1/1 (`check_cable`)

Gather the interface's physical-layer evidence before touching anything:

```
show interface ethernet 1/1/1
show interface ethernet 1/1/1 transceiver     # Rx/Tx power, temperature, alarms
show interface ethernet 1/1/1 statistics | grep -i "fcs\|crc\|error"
show logging | grep -i "ethernet1/1"
```

Check the spine end for the same window (`show logging` on spine-01) to rule out a remote-end cause. Physically inspect: transceiver fully seated at both ends, cable undamaged, fiber end-faces clean. Low/absent Rx power with a good remote Tx means the cable or local optic is the fault — replace it and skip to Step 3.

### Step 2 — Bounce the interface to re-negotiate link (`bounce_interface`)

If physical inspection is clean (or after replacing optics/cable), bounce the port to force renegotiation:

```
configure terminal
interface ethernet 1/1/1
shutdown
no shutdown
exit
```

Watch for the link to come up within ~30 s. If the port immediately flaps or stays down with known-good optics and cable, test the transceiver in a spare port to isolate port hardware vs. transceiver.

### Step 3 — Verify link state, LLDP neighbor, and BGP reconvergence (`verify_convergence`)

Link-up alone is not done — confirm the fabric actually reconverged onto it:

```
show interface status | grep 1/1/1          # expect "up"
show lldp neighbors                          # spine-01 re-learned on Ethernet1/1
show ip bgp summary                          # peer 10.0.0.1 Established, prefixes received
show ip route <spine-prefix>                 # ECMP path count restored (e.g. 3 -> 4)
```

Then confirm error counters stay flat under load for 15 minutes (`show interface ethernet 1/1/1 statistics`). A link that comes up but resumes accumulating FCS errors is still degraded — replace the optics rather than closing the incident.

## Escalation

- Optics/cable replaced but the port still won't link, or errors persist on known-good media → open a Dell support case for the switch (possible port/ASIC fault); include `show tech-support` output.
- The same uplink flaps repeatedly across days despite replacement → treat as structured-cabling fault and engage facilities to test the fiber path.
- Multiple uplinks or multiple leaves losing links in the same window → escalate as a spine-side or power/facilities event, not a per-port fault.
