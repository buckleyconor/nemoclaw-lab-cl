# ADR-015: Install the NemoClaw CLI without triggering its default onboarding

**Status:** Proposed — prototype only (`deploy/scripts/install-nemoclaw-cli.sh`). Not wired into `make bootstrap`, and **not yet verified on a clean host**. Supersedes the "Install:" advice in `deploy/scripts/bootstrap.sh` and the `nemoclaw` CLI row removed from `docs/single-node-deployment.md` §2.

## Decision

The lab installs the NemoClaw CLI by cloning the selected upstream ref, **sourcing** `scripts/install.sh`, and calling `install_nemoclaw_before_onboarding` — the installer's phases 1-2 (Node.js, CLI install + verify) — then stopping. Onboarding stays exclusively in `deploy/scripts/onboard-openclaw.sh`, which runs later, after `run-inference-proxy.sh` is live.

The documented `curl -fsSL https://www.nvidia.com/nemoclaw.sh | bash` is **not** used by the automated path, because it also onboards.

## Context

**(a) The installer onboards by default, and its onboard is not ours.** `scripts/install.sh` is three phases; phase 3 is `step 3 "Onboarding"`, which calls `run_onboard` → a bare `nemoclaw onboard` with no `--from` and no `--name`. That builds the *managed* sandbox image. This lab's onboard (`onboard-openclaw.sh`) is the same CLI verb with different arguments — `--agent openclaw --name "$SANDBOX_NAME" --from "$BUILD_DIR/Dockerfile"`, plus `NEMOCLAW_PROVIDER=custom` and our endpoint. The two are mutually exclusive, not merely redundant.

**(b) Ordering makes it unfixable in the installer's direction.** Our onboard bakes `LLM_BASE_URL` into the sandbox, which is why `onboard-openclaw.sh` refuses to run until the inference proxy answers ("It must be live BEFORE onboarding — the URL is baked into the sandbox"). Phase 3 runs before our `.env`, our proxy, and our Dockerfile exist. Even a *successful* default onboard produces a sandbox pointed at the wrong endpoint that we would have to destroy.

**(c) Why not `--defer-onboarding`.** It is Hermes-only and fatal otherwise: `validate_deferred_hermes_onboarding_request` calls `error "--defer-onboarding currently requires NEMOCLAW_AGENT=hermes."`, and `error()` is `error_with_status 1` — the install aborts before anything lands. Satisfying the gate is worse: `NEMOCLAW_AGENT=hermes` selects `_CLI_BIN="nemohermes"`, a different product and a different binary name, so `bootstrap.sh`'s `command -v nemoclaw` would still fail. The flag also requires zero registered sandboxes *and* both `NVIDIA_INFERENCE_API_KEY` and `NVIDIA_API_KEY` unset — it is a credentials-absent escape hatch, not a general "install only" switch.

**(d) Why not the other skip paths.** Phase 3 is also skipped when sandboxes already exist ("Existing sandboxes recovered; skipping generic onboarding") or when `NEMOCLAW_SINGLE_SESSION=1` aborts on detecting them. Both require a sandbox to be registered already, which is never true on the fresh host that automation targets.

**(e) Why sourcing is the seam.** The payload guards its own entrypoint — `if [[ "${BASH_SOURCE[0]:-}" == "$0" ]] ...; then main "$@"; fi` — so sourcing defines every function without running phase 3. Phases 1-2 are already factored into one function, `install_nemoclaw_before_onboarding`, precisely because upstream separates "install" from "onboard" internally. We set `NEMOCLAW_BOOTSTRAP_PAYLOAD=1` so `is_source_checkout` returns false and `install_nemoclaw` takes the managed install-from-GitHub branch into the state root — byte-for-byte the same install a real `curl | bash` performs — rather than `npm link`-ing our throwaway clone.

**(f) Why not vendor the install ourselves.** `install_nemoclaw` is clone + `npm install` + `npm run build:cli` + plugin build + `npm link` from a git checkout, not a published registry package. Reimplementing it would also mean owning Node bootstrap, npm permission repair, legacy gateway retirement, and OpenShell version reporting — every one of which is a phase-1/2 step we get for free by calling upstream's own function.

## Consequences

**Positive:**

- The unattended deploy stops fighting the installer. No throwaway sandbox, no wasted managed-image pull, no ~10-minute build discarded on every provision.
- Onboarding happens exactly once, in the one place that knows about the proxy, the Dockerfile, and the CLI-version↔image coupling (§2 of the deployment guide).
- The CLI install itself is unchanged from upstream's managed path, so version pinning (`NEMOCLAW_INSTALL_REF`) and the `nemoclaw --version` → sandbox base tag derivation in `deploy/scripts/lib/nemoclaw.sh` keep working as documented.

**Negative:**

- **`install_nemoclaw_before_onboarding` is an internal function, not a public interface.** Any upstream release may rename or restructure it, and our deploy breaks at install time with no deprecation warning. The prototype asserts `registered_sandbox_count` is still `0` afterwards so a silent regression to "phase 3 ran anyway" fails loudly rather than corrupting the deploy, but it cannot defend against the function simply disappearing.
- **Phases 1-2 skip `main()`'s third-party software notice prompt.** The script therefore requires `NEMOCLAW_ACCEPT_THIRD_PARTY_SOFTWARE=1` explicitly rather than silently bypassing a licence gate.
- **It also skips `prepare_installer_host` / `ensure_docker`.** `make bootstrap` already checks Docker, the compose plugin, and group membership, so this is not a regression for our path — but this script is not a drop-in replacement for the public installer on an unprepared host.
- **Unverified.** Neither the sourced path nor the `--fresh` interaction below has been exercised on a clean machine. Do that before wiring it into `make bootstrap`.

## Follow-ups

1. **Add `--fresh` to our own onboard.** A failed or interrupted install-time onboard leaves `onboard-session.json` behind; the installer's classifier treats a `failed` session as "user must choose", and upstream's own comment records this dead-ending at the CLI non-interactive resume guard with "no recovery path for curl|bash installs". `onboard-openclaw.sh` does not pass `--fresh`, so an unattended run on a host with leftover session state can hang there. This is worth fixing regardless of whether this ADR is adopted.
2. **Ask upstream to widen `--defer-onboarding` to the openclaw agent.** The mechanism exists; the gate is one `if`. That would replace this entire ADR with a supported flag, and is the only durable fix.
3. **Restore a CLI row to the deployment guide's prerequisites table** once this path is settled, describing the real sequence rather than the bare `curl | bash`.
