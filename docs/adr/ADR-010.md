# ADR-010: LLM-driven tool-calling loop replaces the hardcoded agent sequence

**Status:** Accepted

## Decision

The agent's core decision loop (`agent/loop.py`) is redesigned from a hardcoded
11-step procedural sequence into a bounded, LLM-driven tool-calling loop. The
LLM (Qwen 3.6 35B via the existing self-hosted vLLM endpoint) dynamically
chooses which MCP tool to call next — `monitor_list_events`,
`monitor_get_asset`, `monitor_list_assets`, `logs_get_bundle`, `kb_search`,
`notify_post_activity`, or `remediation_propose` — based on its system prompt
(`soul.md` plus the five `infra-sentinel-*` `SKILL.md` files, loaded verbatim
minus YAML frontmatter) and the tool results fed back to it turn by turn. The
tool catalogue is generated at runtime from the MCP server's own
`list_tools()` response and translated into OpenAI-style `tools=[...]`
function schemas (dotted MCP names such as `monitor.list_events` become
underscored function names such as `monitor_list_events` for the model,
with the harness maintaining the reverse mapping to dispatch real MCP calls).

`agent/loop.py` keeps its file path and `run_agent_loop()` keeps its existing
signature (`tools, gateway_client, llm_client, loaded_pack, *,
approval_timeout, poll_interval`), so `agent/main.py` requires no changes.
Only the function's internals change.

The two isolated one-shot LLM calls in the old design (`SIGNATURE_EXTRACTION_SYSTEM`,
`FAULT_ANALYSIS_SYSTEM` in `agent/llm.py`) are removed. They existed because
the old harness, not an LLM, was driving the loop and needed to delegate
interpretation to a model at two specific points. In the new design the LLM
*is* the loop — it reads the log bundle via `logs_get_bundle` and identifies
the error signature as part of its own reasoning, with no need to hand off
to a separate nested completion call.

Four things remain deterministic harness code, entirely outside the LLM's
tool-calling surface: registering the `FaultEvent`, all fault status
transitions, gating on human approval, and calling the token-bearing
`remediation.execute` MCP tool. The LLM is never given `remediation.execute`'s
schema and never sees an approval token in any message it reads.

## Context

The lab's headline claim is that an AI agent *dynamically decides* to
monitor, diagnose, notify, and remediate via skills. Today that claim is not
true at the code level: `agent/loop.py`'s own docstring enumerates 11 fixed
steps mapped onto 4 skills, the LLM is called twice as an isolated
subroutine with no `tools=`/`tool_choice` anywhere in the codebase, and the
five `infra-sentinel-*/SKILL.md` files — despite being written in a
Claude-Code-style skill format with `Steps` and `Notes` sections — are never
loaded or parsed by any code (`grep -rn "SKILL.md" agent/ services/` returns
zero hits). The "skills" are documentation about a script, not instructions
consulted by a reasoning agent.

Several sub-problems had to be solved to close this gap without breaking
existing invariants:

**(a) Surfacing MCP tool schemas to the LLM.** `mcp==1.28.1`'s
`ClientSession.list_tools()` already returns each tool's `name`,
`description`, and JSON-Schema `inputSchema` (FastMCP auto-generates this
from the typed Python signatures in `services/mcp_tools/server.py`). This is
converted once per agent connection into OpenAI's
`{"type": "function", "function": {"name", "description", "parameters"}}`
shape and passed as `tools=[...]` on every `chat.completions.create()` call
(`openai==2.44.0` supports this fully). One concrete translation problem: MCP
tool names use dots; OpenAI/vLLM function-calling name fields are
conventionally restricted to `[a-zA-Z0-9_-]`. The harness translates dotted
MCP names to underscored function names in the schema sent to the model, and
keeps the reverse mapping to dispatch the model's chosen function name back
to the real MCP call.

**(b) Making SKILL.md content live.** The harness reads all five
`agent/skills/*/SKILL.md` files, strips YAML frontmatter, and concatenates
them (guide first for orientation, then the four phase skills) into the
system prompt alongside `soul.md`. Editing a skill's prose now changes agent
behaviour without a Python change — the actual point of having skills at
all. This required rewriting the five files themselves (done in the same
change as this ADR): the previous bodies were written for a deterministic
caller and contained literal step numbers, exact activity message templates,
and specific delay timings, which if fed to the LLM as-is would just
re-encode the old fixed sequence in prose instead of code.

**(c) Preserving the ADR-004 HITL invariant.** This is the safety-critical
decision. Two approaches were considered:

- **Expose `remediation.execute` directly to the LLM, and inject the
  approval token into a tool result once available** — rejected outright.
  This re-creates exactly the "server-side token, passed to agent in
  context" pattern ADR-004 already rejected: the token would sit in
  conversation history the LLM reads, and a prompt-injection payload
  embedded in log text or a KB article could induce the model to replay or
  misuse it.
- **Split remediation into a propose/execute pair with different trust
  levels** ✅ — a new, lightweight MCP tool, `remediation.propose`, is added
  to `services/mcp_tools/server.py`. It takes `fault_event_id` and
  `step_ids` (no token), and its only side effect is to `PATCH` the fault to
  `awaiting_approval` and record the proposed steps — the dynamic-agent
  equivalent of the old loop's steps 7–8. This is the *only*
  remediation-related tool the LLM's `tools=[...]` payload ever contains.
  `remediation.execute` itself is unchanged — same signature, same
  server-side token validation — but is **never included** in the tool
  schema sent to the model. Once the LLM calls `remediation.propose` (or the
  harness decides the bounded loop is done), deterministic harness code
  takes over exactly as the current loop's steps 9–10 do: poll
  `GET /api/faults/{id}/token` out-of-band, and only once a token is
  retrieved, call `remediation.execute` directly as a plain Python function
  call, not a model-issued tool call. As defense in depth, the harness's
  tool-dispatch table explicitly allowlists the function names it will act
  on and silently ignores any tool call the model emits outside that
  allowlist, in case a model hallucinates a call to a tool it was never
  given.

  This preserves every property in ADR-004's Decision and Positive
  consequences unchanged: the token still never enters LLM context, is still
  minted only on operator click, is still single-use and event-bound, and
  the LLM's only power over remediation is to propose — never to execute.

**(d) Making "notify" a real, LLM-controlled skill.** In the old design,
activity narration was an inline harness helper (`_act()` in `loop.py`)
posting scripted, hardcoded message strings — not something the agent
decided to do. For "notify" to be an actual skill the agent controls (as
opposed to a mechanical side effect of the other three), a new MCP tool,
`notify.post_activity`, is added — LLM-callable, takes `fault_event_id`,
`step`, and a free-text `message` the LLM composes itself. This tool is safe
by construction: it only writes a display string to the activity feed, with
no effect on fault status or infrastructure state, so it needs none of the
propose/execute trust separation that remediation needs.

**(e) Preserving vertical-blindness (ADR-007/008).** The MCP server does not
vary per pack — `list_tools()` returns the same tool set regardless of
`PACK_ID`, so the LLM's available actions are vertical-blind by construction.
`soul.md` and the skill files, however, already contain flagship-vertical
language (GPU cluster, Redfish, iDRAC) that was previously cosmetic (nothing
read it) and becomes live model input under this redesign — a real,
newly-consequential gap, tracked as a Negative consequence below rather than
silently fixed here, since properly fixing it means templating `soul.md`
from pack content, a code change out of scope for this documentation-only
turn.

**(f) The determinism tension with ADR-002.** ADR-002 guarantees a
deterministic, rehearsable demo flow. A tool-calling loop that lets the model
choose the order and count of its own actions introduces a form of
non-determinism ADR-002 did not anticipate. Two approaches were considered:

- **Unbounded agentic loop, model decides when it's fully done** — most
  "realistic," but risks runaway tool-call loops or a model that forgets to
  call `remediation.propose` mid-demo. Rejected as too risky for a timed lab
  session.
- **Bounded ReAct loop with a hard turn cap, temperature 0, and a strong
  system prompt** ✅ — a hard cap (e.g. 8 tool-call turns per fault cycle)
  bounds worst-case runtime and cost; `temperature=0` (already
  `OpenAILLMClient`'s default) makes each turn's sampling greedy; the system
  prompt states the natural detect → diagnose → search → propose
  progression as a strong recommendation without hardcoding it as literal
  enforced steps. Combined with ADR-002's canned, rotated scenarios and
  fixed log bundles, this should make the tool-call sequence highly
  reproducible in practice — but this is *practically expected*
  reproducibility, not the *guaranteed* determinism ADR-002 describes today:
  greedy decoding against an identical prompt is not formally guaranteed to
  be bit-identical run-to-run, and the sequence and count of tool calls is
  now a model decision, not code. If the turn cap is exhausted without a
  `remediation.propose` call, the harness falls back to the pre-redesign
  deterministic behaviour (use the KB/scenario steps directly) so a demo
  session never simply stalls.

**(g) `agent/loop.py`'s file path.** Kept unchanged, deliberately, to
minimise doc churn: README's project-layout line and
`docs/VERTICAL-PACK-GUIDE.md`'s claim that "no changes to `agent/loop.py`,
`agent/skills/`, or `agent/soul.md` are required for a new vertical" both
continue to hold, because this redesign changes the loop's internal
behaviour and the meaning of the skill files, not their location or their
per-vertical neutrality.

## Consequences

**Positive:**

- The lab's headline claim — "an AI agent dynamically decides to
  monitor/diagnose/notify/remediate via skills" — becomes literally true
  instead of aspirational.
- SKILL.md files become live, load-bearing content for the first time:
  changing agent reasoning at the skill level no longer requires a Python
  change, extending the "content not code" spirit already established for
  packs (ADR-007) to the agent's own instruction set.
- "Notify" becomes a genuine agent-controlled skill (via
  `notify.post_activity`) rather than a scripted side effect — closing a gap
  that existed even in the original 4-skill design, where notification was
  never actually delegated to the agent.
- MCP tools that already exist server-side but are unused by the current
  loop (`monitor.get_asset`, `monitor.list_assets`) become available to the
  LLM automatically via `list_tools()`, with no bespoke Python plumbing.
- Removing the two nested one-shot LLM calls simplifies `agent/llm.py` and
  removes a source of latency (no more "call the LLM, then call it again"
  — one reasoning pass covers both).
- The HITL guarantee is preserved unweakened: `remediation.execute` keeps
  its exact current signature, server-side validation, and audit
  properties — this redesign adds a proposal step in front of it, it does
  not touch the execution gate itself.
- `agent/loop.py`'s file path, `agent/main.py`'s call signature, and the
  pack contract are all unchanged at the interface level, so this redesign
  is additive from every other service's perspective.

**Negative:**

- **Unverified whether Qwen 3.6 35B on this specific vLLM deployment
  reliably supports OpenAI-style tool-calling.** Must be validated with a
  small spike (a scripted call to the vLLM endpoint with `tools=[...]` and
  `tool_choice="auto"`) *before* implementation begins. If unreliable, this
  ADR's design needs a fallback (manually-parsed ReAct text protocol
  instead of native tool-calling).
- MCP tool names are dotted; OpenAI/vLLM function-calling name fields are
  conventionally restricted to `[a-zA-Z0-9_-]`. The dot-to-underscore
  translation layer must be verified against both `openai==2.44.0`'s
  client-side validation and vLLM's server-side enforcement — untested
  today.
- ADR-002's determinism guarantee is weakened from "guaranteed" to
  "practically expected" for the sequence and count of tool calls (scenario
  content itself is unaffected). A rehearsal pass before each live demo
  session becomes recommended practice rather than provably unnecessary.
- `soul.md`'s Identity section is written specifically for the flagship AI
  Infrastructure vertical. Because `soul.md` becomes live LLM input under
  this redesign, running the dynamic loop under a different `PACK_ID` (e.g.
  `laptop-fleet`, already active) would feed the model an identity claiming
  it watches a GPU cluster while it actually monitors laptops — a
  pre-existing tension with ADR-008's vertical-blind claim that becomes
  newly behaviourally relevant. Not resolved by this ADR; flagged for
  near-term follow-up (e.g. templating the Identity section from
  `pack.yaml` fields).
- Adds two new MCP tools (`remediation.propose`, `notify.post_activity`) to
  `services/mcp_tools/server.py` and a tool-dispatch allowlist — real code
  changes, not covered by this documentation-only turn. This ADR records
  the agreed contract for that follow-up implementation.
- The turn-cap fallback to deterministic KB/scenario-driven remediation
  means the "dynamic" behaviour is a best-effort layer on top of an
  unchanged deterministic safety net: the demo's reliability floor is
  unchanged, only the common-case behaviour becomes genuinely agentic.
