# ADR-012: Embedded operator terminal in the lab UI

**Status:** Accepted — implemented (see `docs/SPEC-EMBEDDED-TERMINAL.md` for the full functional spec and verification status)

## Decision

Add an embedded terminal panel to the dashboard SPA, placed below the Operator Dashboard, giving the operator a real interactive shell on the lab host for configuring the NemoClaw agent (editing SOUL.md / SKILL.md, running `nemoclaw`, `openclaw`, and `openshell` commands).

The terminal is backed by a new **host-side terminal daemon** (`services/terminal/`, FastAPI) that runs on the lab host via `uv run` — deliberately *not* a Compose service, mirroring the host-process pattern ADR-011 established for the agent itself. The data path is:

```
Browser (xterm.js)
  ⇄ WS /api/terminal/ws            (gateway container — proxy only)
    ⇄ ws://host.docker.internal:8005/ws   (bearer token injected by the proxy)
      ⇄ PTY running `bash -l`      (terminal daemon, host, user democenter)
```

The frontend renders the terminal with xterm.js (`@xterm/xterm` + `@xterm/addon-fit`), themed from the existing UI design tokens.

## Context

Four constraints drove this shape:

- **The CLIs the operator needs live on the host, not in containers.** `nemoclaw`, `openclaw`, and `openshell` are installed at `~/.local/bin/` on the lab host, with their state under `~/.nemoclaw` and `~/.local/state/openshell`, and they manage Docker-based OpenShell sandboxes via the host Docker daemon. A terminal endpoint inside the containerized gateway could not run any of them. The only alternatives — mounting the Docker socket and host binaries into the gateway container, or baking the CLIs into the image — break the container boundary badly and still miss host state. A small host daemon, like the agent itself (ADR-011), is the honest topology.

- **Editors require a real PTY.** The requirement includes running nano/vi to edit SOUL.md and SKILL.md files. Full-screen terminal applications need a pseudo-terminal with window-size control and `TERM=xterm-256color` — a request/response "command runner" API cannot support them. This forces the PTY ⇄ WebSocket ⇄ xterm.js architecture (the same pattern used by VS Code's integrated terminal, JupyterLab, and ttyd).

- **The lab is accessed through a single-port SSH tunnel.** Operators reach the UI via `ssh -L 8001:localhost:8001` to the lab host. Proxying the terminal WebSocket through the gateway on the same port 8001 preserves that workflow unchanged; exposing the daemon on a second port would require every operator to tunnel a second port. The gateway already reaches host processes via `host.docker.internal` (the ADR-011 webhook wake-up uses the same hop).

- **WebSocket, not SSE.** The UI's existing live channel (`GET /api/events`) is Server-Sent Events, which is server→client only. A terminal needs low-latency bidirectional byte streams plus in-band control messages (resize). `websockets` is already resolved in `uv.lock` via `uvicorn[standard]`, so the gateway proxy adds no new backend dependency.

## Consequences

**Positive:**
- Operators can configure the agent (SOUL.md, SKILL.md, policies, sandbox lifecycle) directly from the lab UI, without a separate SSH session — including during guided lab-guide walkthroughs.
- Full fidelity: paste, editors, interactive commands (`nemoclaw infra-sentinel connect`, `openclaw tui`) all work, because it is a real PTY rather than a restricted command wrapper.
- No change to the operator access model: same port, same tunnel, same origin as the rest of the dashboard.
- The daemon reuses the repo's existing stack (FastAPI + uv) and the host-process operational pattern already established for the agent.

**Negative / security:**
- **This exposes a full host shell (as the lab user) to anyone who can reach the dashboard origin.** That is the same trust boundary as the existing Approve/Deny buttons, and is acceptable for a private, single-operator demo lab behind an SSH tunnel — but it is categorically unacceptable in a shared deployment. Mitigations required by the spec: the daemon binds a host-local address only (loopback by default; the docker bridge IP where the containerized gateway must reach it — on Linux, `host-gateway` resolves to the bridge, not loopback); the gateway proxy injects a shared bearer token (`TERMINAL_TOKEN`, same pattern as `OPENCLAW_HOOK_TOKEN`) that the browser never sees; and a `TERMINAL_ENABLED` flag gates the whole feature. **The M9 (Kubernetes, 30-user) deployment MUST ship with `TERMINAL_ENABLED=0`.** Port 8005 must never be exposed off-host.
- A new host process to operate: started via `deploy/scripts/run-terminal.sh` (or a Makefile target); if it is down, the panel shows disconnected. A systemd user unit is a possible later hardening, not part of this ADR.
- New frontend dependencies (`@xterm/xterm`, `@xterm/addon-fit`) and a new transport in the architecture diagram (browser ⇄ gateway becomes HTTP + SSE + WS).
- Terminal sessions are ephemeral: each WebSocket connection gets a fresh PTY, so a page reload loses shell state (a `tmux`-based attach wrapper is noted in the spec as an optional enhancement, not a commitment).
