# ADR-004: HITL approval enforced server-side via single-use event-bound tokens

**Status:** Accepted

## Decision

Human-in-the-loop approval is implemented as a single-use cryptographic token minted by the Gateway at the moment an operator clicks Approve. The token is stored server-side and retrieved by the agent over a trusted internal path — it never appears in the LLM prompt or agent context.

## Context

The core safety claim of the demo is that an AI agent cannot remediate infrastructure without explicit human authorisation. Several implementation approaches were considered:

- **Agent self-reports "approved"** — the agent posts a message saying it has approval and proceeds. Trivially bypassable by prompt injection.
- **Operator sends token in chat** — a human types an approval code into the chat interface. The agent reads it from context, so prompt injection still works.
- **Server-side token, passed to agent in context** — better, but the token is still in the LLM's context window and could be extracted by an adversarial prompt.
- **Server-side token, retrieved out-of-band** ✅ — the token exists only in the Gateway store. The agent calls `GET /api/faults/{id}/token` immediately before calling `remediation.execute`. The token is never in the LLM context. Prompt injection cannot manufacture a valid token.

The token is also event-bound: it is created for a specific `fault_event_id` and consumed on first use by the MCP remediation tool. Replay across fault events is rejected.

## Consequences

**Positive:**
- Prompt injection cannot bypass the approval gate — no token exists in any text the LLM can read.
- The gate is demonstrably injection-proof and easy to explain to audiences.
- Single-use prevents replay: approving one fault cannot remediate a different fault.
- Token validation lives in `services/mcp_tools/token_store.py` — auditable, independent of the agent.

**Negative:**
- Requires the Gateway and MCP Tools services to be trusted by each other (same internal network). Not suitable for zero-trust inter-service architectures without mTLS.
- If the agent times out waiting for a token (currently 1 hour), the fault remains in `awaiting_approval` state in the gateway until a Reset is performed.
- Re-approving a denied fault requires a new fault cycle (deny closes the approval window; the agent is no longer polling that fault).
