# ADR-013: Restricted, per-tenant operator terminal for M9 (Kubernetes, 30 tenants)

**Status:** Accepted — implemented (`services/terminal/console.py`, `deploy/scripts/run-terminal-tenant.sh`, `deploy/helm/nemoclaw/templates/terminal-secret.yaml`). Supersedes ADR-012 §"Negative/security" and `docs/SPEC-EMBEDDED-TERMINAL.md` §7 item 4 for this specific design only.

## Decision

The embedded operator terminal (ADR-012/M12) gains a second mode, selected by a new `TERMINAL_MODE` env var on the terminal daemon:

- `shell` (default, unchanged): today's full `/bin/bash -l` login shell — local Compose dev only.
- `restricted`: the daemon spawns `services.terminal.console` onto the PTY instead of a shell — a numbered menu of exactly six hardcoded edit targets (`SOUL.md`, `AGENTS.md`, and the four `infra-sentinel-{monitor,diagnose,notify,remediate}` skills). Every sandbox path is a compile-time constant; no operator-typed string ever reaches a subprocess argv.

Each menu selection: best-effort `nemoclaw <sandbox> download` seeds a scratch copy from the sandbox, `vim -Z` (restricted vim — refuses `:!`, `:sh`, suspend, and writing any file other than the one given) edits it on the real PTY, then `nemoclaw <sandbox> upload` (for `SOUL.md`/`AGENTS.md`) or `nemoclaw <sandbox> skill install` (for skills) pushes it back — both real, verified CLI subcommands, matching what `deploy/scripts/onboard-openclaw.sh` already uses for the same files.

This is deployed **per tenant, one daemon process per sandbox** on the external agent host (`deploy/scripts/run-terminal-tenant.sh <tenant> <sandbox-name> <port>`), extending ADR-011's existing "peer host process" pattern rather than moving the sandbox into the cluster. Each tenant's Helm release points its own `terminal.wsUrl`/`terminal.token` (new `deploy/helm/nemoclaw/templates/terminal-secret.yaml`, mirroring the existing `openclawHook` secret exactly) at that dedicated port; `services/gateway/terminal.py`'s proxy is unchanged — it only ever forwards to whatever `TERMINAL_WS_URL` it's configured with.

## Context

**(a) Why this needed its own ADR.** ADR-012 §"Negative/security" and `docs/SPEC-EMBEDDED-TERMINAL.md` §7 item 4 both hard-mandate `TERMINAL_ENABLED=0` for the M9 shared/30-tenant deployment, because the only thing on offer at the time was a full unrestricted shell behind one shared secret — "whoever reaches port 8001 is the operator" is not an acceptable trust model once 30 independent tenants share a cluster. That mandate is correct for the design it was written against. It does not follow that *no* terminal can ever be safe there — a restricted, per-tenant, non-shell session changes the threat model enough to warrant revisiting the decision, hence a new ADR rather than a quiet edit.

**(b) Why the sandbox stays on an external host, not an in-cluster pod.** ADR-011(b) already rejected nesting OpenShell inside Compose because `nemoclaw onboard` drives Docker directly to build/manage its own sandbox, and nesting that would require Docker-in-Docker, "directly undermining OpenShell's own security purpose." The identical objection applies to a K8s pod (privileged DinD or a sysbox/kata sidecar). `deploy/helm/nemoclaw/templates/resourcequota.yaml`'s `persistentvolumeclaims: "0"` cap — flagged in ADR-011 as a concrete future blocker for any in-cluster sandbox — would also need a per-tenant exception. Keeping the sandbox external avoids both: it is the same "one external Docker host running N sandboxes" shape as today, just parameterized per tenant, with zero new cluster attack surface or quota changes.

**(c) Why a restricted PTY instead of a guided web form.** A form (pick a skill, edit in a textarea, click Install) would be strictly safer — no PTY, no shell process at all — but the requirement was specifically to keep `vi`'s interactive editing experience (the operator's stated workflow pastes content into `vi` and saves). `vim -Z` (restricted mode) is the standard, well-precedented Unix mechanism for exactly this: an interactive full-screen editor confined to one named file with `:!`, `:sh`, suspend, and `:w <other>` all refused. Regex-filtering a raw PTY byte stream was rejected as fragile and easily bypassed (shell metacharacters, `vi`'s own escapes); the console avoids that problem entirely by never running a real shell in the first place — the PTY's only occupant is the Python menu program and, transiently, `vim -Z`.

**(d) Why one daemon process per tenant, not one multiplexing daemon.** A single process serving all 30 tenants (looking up a sandbox name per bearer token) would need a new token→tenant store and widens one process's blast radius to every tenant. One dedicated process per tenant — literally `deploy/scripts/run-terminal.sh`, parameterized by `SANDBOX_NAME`/port/token — needed no new state-management code and keeps a daemon crash or compromise scoped to its own tenant, matching the "one sandbox per tenant" shape already chosen for (b).

**(e) Guide skill.** The menu's second item edits `AGENTS.md`, not a nonexistent fifth `infra-sentinel-guide` skill directory — ADR-011(f) already folded that content into `AGENTS.md` as always-injected orientation context, and `openclaw/skills/` only ever had four directories on disk.

## Consequences

**Positive:**
- M9 tenants get the SOUL.md/skill editing workflow ADR-012 promised, without reversing ADR-011's rejection of Docker-in-Docker or touching the per-tenant resource quota.
- No changes needed to `services/gateway/terminal.py` or the wire protocol at all — the proxy, PTY pump, resize handling, and exit-frame logic are identical in both modes; only what's spawned onto the PTY differs.
- Zero shell-injection surface in the new code path: every sandbox path is a compile-time constant, every subprocess call uses a literal argv list, never `shell=True`.
- `shell` mode (local dev) is completely unaffected — same default, same tests pass unchanged.

**Negative:**
- 30 tenants means 30 host processes with no systemd units in v1 (same operational gap already tracked for the existing terminal/hook-relay daemons — restarting after a host reboot is manual).
- `vim -Z`'s guarantees rest on vim's own restricted-mode implementation, not a sandboxed process (no seccomp/namespace/cgroup). It is a well-established mechanism but not a formally verified boundary; a vim CVE that defeats `-Z` would defeat this design too.
- Per-tenant token/port management is manual (`run-terminal-tenant.sh` prints what to put in each tenant's Helm overlay) — no automation ties Helm release creation to daemon provisioning yet.
- Still no in-cluster K8s-native OpenShell/OpenClaw story — ADR-011(g)'s deferred follow-up remains open; this ADR only resolves the terminal's piece of M9, not the agent's.
