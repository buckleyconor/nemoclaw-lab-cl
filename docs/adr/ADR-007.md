# ADR-007: Domain Pack abstraction — verticals are content not code

**Status:** Accepted — see the Amendment on restart semantics below

## Decision

Each industry vertical is expressed as a **Domain Pack** — a directory of YAML files, Markdown KB articles, and raw log bundles — not a code branch or service variant. Switching verticals requires only changing `PACK_ID` in the environment; no code changes, no image rebuilds.

### Amendment — switching a pack does recreate the stack

The original wording said "no service restarts". That is wrong in practice and
was never true of the implementation. `PACK_ID` is resolved **at startup**, and
two pieces of per-pack state live in process memory: `mcp-tools`' FAISS KB index
and the gateway's fault/activity registries. Leaving either in place across a
switch serves the previous vertical's data under the new pack's labels.

`make switch-pack PACK_ID=<id>` therefore rewrites `PACK_ID` in `.env` and does a
full `docker compose down && docker compose up -d`. A plain `up -d` is not enough.
The claim that survives is the one that matters: switching verticals is a
**content** change — no code edits, no image rebuilds, ~15s of downtime.
See `docs/PACK-EXPANSION-PLAN.md` and `deploy/scripts/switch-pack.sh`.

## Context

The agent framework needs to serve AI infrastructure, laptop fleet management, oil & gas, healthcare, financial services, and edge computing verticals — all with the same agent behaviour, the same UI, and the same approval flow. The differentiating content per vertical is:

- What *assets* exist and how they are named
- What *fault scenarios* can be injected
- What *KB articles* describe the remediation
- What *log bundles* the simulator emits
- What *error signatures* the LLM looks for

None of this requires code changes. All of it is expressible as structured content.

The pack format (`pack.yaml` + `scenarios/*.yaml` + `kb/*.md` + `bundles/*.log`) is a content contract. The `libs/common/pack_loader.py` validates it on startup. Services receive the loaded pack via FastAPI `app.state.loaded_pack`.

## Consequences

**Positive:**
- New verticals are created by authoring content, not writing code.
- All verticals share the same Docker images, the same agent loop, the same UI, and the same lab guide structure.
- A single CI pipeline builds and tests all verticals.
- Domain experts (not developers) can author and maintain pack content.
- The lab guide (`docs/lab-guide.html`) reads the `?vertical=` URL param and swaps in vertical-specific text from a JS config table — no separate HTML file per vertical.

**Negative:**
- Verticals with genuinely different agent behaviour (e.g., one that needs a different approval flow or different MCP tools) cannot be expressed as content alone — they require framework changes.
- Pack authors must follow the YAML schema exactly; validation errors at startup are the only feedback mechanism (no schema editor or lint tool yet).
- `MonitoringAdapter` type (`redfish` vs `generic`) is a code-level choice that must be made at pack authoring time; a new protocol requires a new adapter.
