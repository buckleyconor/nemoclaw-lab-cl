# ADR-003: CPU-only service images — LLM is an external endpoint

**Status:** Accepted — amended by [ADR-014](ADR-014.md) (shared lab endpoint,
host inference proxy, repoint flow; the config var is now `LLM_BASE_URL` —
`VLLM_BASE_URL` below is the legacy name, still read by doctor.sh as a
fallback)

## Decision

All Python service images are built as multi-architecture (`linux/amd64`, `linux/arm64`) with CPU-only ML dependencies (fastembed ONNX, FAISS-cpu). The LLM is an external vLLM endpoint referenced via `VLLM_BASE_URL` — it is not a container in the compose stack.

## Context

The demo runs across several environments:
- Apple Silicon MacBook (arm64) — developer
- Dell GB10 Copilot+ PC (arm64, Snapdragon X Elite) — lab delivery
- Dell PowerEdge (amd64, Linux) — production delivery

Bundling a GPU-backed LLM inside the compose stack would require CUDA drivers, GPU passthrough, and nvidia-container-toolkit — incompatible with arm64 dev machines and impractical for a quick-start demo. The semantic KB search (fastembed + FAISS) must run in-container, but embedding inference over a 384-dim model is fast on CPU.

## Consequences

**Positive:**
- Single `docker compose up` works on any platform without GPU setup.
- Service images are small (no CUDA base layers).
- LLM endpoint is swappable — set `VLLM_BASE_URL` to a local vLLM instance, a cloud API, or a GB10 NPU service.
- fastembed uses ONNX Runtime, optimised for CPU and arm64 NEON.

**Negative:**
- The LLM is an external dependency — the demo degrades if the endpoint is unreachable (stub client falls back to hardcoded signatures, but analysis prose is blank).
- KB index cold-start: FAISS index is built from pack KB articles on first request (~2–4 s depending on article count).
- Cannot demonstrate GPU-accelerated inference inside the compose stack.
