# ADR-006: In-memory store (dev) → Redis (prod) for runtime state

**Status:** Accepted

## Decision

The Gateway uses an in-memory Python dataclass store (`GatewayStore`) for development and single-instance demos. A `RedisGatewayStore` implementation exists for production multi-instance deployments. All store access is via `async def` methods so the router switches stores without any router changes.

## Context

The Gateway holds all runtime state: fault events, activity log, notifications, asset health, and pending approval tokens. For a single-host demo, in-memory state is sufficient — it resets cleanly on container restart (or via `POST /api/presenter/reset`) and has zero external dependencies.

For production delivery (30+ concurrent lab participants, multi-node Kubernetes):
- Each gateway replica needs shared state so any replica can serve any client.
- Fault events and approval tokens must survive a gateway pod restart.
- Redis is the standard choice: fast, durable (with AOF), and supported by Charmed K8s addons.

The abstraction is enforced by the identical `async def` signatures on both classes. Switching is done at startup by setting an env var; no router code changes.

## Consequences

**Positive:**
- Zero external dependencies for `docker compose up` — in-memory store works out of the box.
- Redis store is a drop-in for production without changing any API or routing logic.
- The `GatewayStore` async interface makes unit testing straightforward — mock or in-memory, same API.

**Negative:**
- The in-memory store loses all state on container restart. For a live demo this means a Reset is required after restarting the gateway.
- Redis store requires a running Redis instance and additional env vars (`REDIS_URL`).
- Two store implementations must be kept in sync when new state fields are added (e.g., `remediation_step_labels` required updates to both).
