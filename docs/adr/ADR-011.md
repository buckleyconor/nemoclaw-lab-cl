# ADR-011: Replace the bespoke Python agent runtime with real NemoClaw/OpenClaw

**Status:** Accepted

## Decision

The hand-built, bespoke Python agent runtime introduced in ADR-010
(`agent/loop.py`'s bounded ReAct tool-calling loop, `agent/main.py`'s polling
process, `agent/llm.py`'s direct `openai.AsyncOpenAI` client) is retired and
replaced by a real deployment of NVIDIA's NemoClaw reference stack — OpenClaw
running inside an OpenShell-hardened sandbox, installed and managed via
`nemoclaw onboard`. This corrects a gap present since milestone M6:
`agent/config.yaml` has referenced the real product by name, version, and
install command since that milestone, but no code ever acted on it.

`agent/soul.md` and the five `agent/skills/*/SKILL.md` files are migrated
(not deleted) into a new `openclaw/` workspace directory as `SOUL.md` and
OpenClaw skills, with light content edits only (provider-neutral language,
tool-name phrasing). A new TypeScript OpenClaw plugin,
`openclaw/plugins/nemoclaw-infra-tools/`, exposes our seven LLM-facing MCP
tools (`monitor.list_events`, `monitor.get_asset`, `monitor.list_assets`,
`logs.get_bundle`, `kb.search`, `notify.post_activity`,
`remediation.propose`) as native OpenClaw tools by acting as an MCP client
against the existing, unmodified `services/mcp_tools/server.py`.
`remediation.execute` is never registered by this plugin — absent from the
manifest's `contracts.tools`, absent from its dispatch table, and the plugin
hard-fails at load time if the MCP server's own tool listing ever includes
it, mirroring the three-layer defense `agent/tools.py`/`agent/loop.py` used
under ADR-010.

Deterministic, LLM-excluded harness responsibility for the approval gate
moves from `agent/loop.py` (deleted) into `services/gateway/router.py`:
`post_decision()`'s approved branch now retrieves/mints the token and calls
`remediation.execute` directly, server-to-server, synchronously on approval —
replacing the old poll loop with an immediate, race-free trigger. The token
still never enters any LLM context.

The fault-monitoring cadence becomes a webhook-driven Standing Order
(`openclaw/AGENTS.md`), fired by the Orchestrator/Gateway the instant a
scenario is injected, with a Cron poll as a redundant safety net — not
Heartbeat, whose documented 30-minute default is unusable for live-demo
pacing.

`docker-compose.yaml` drops the `agent` service and its LLM env anchor
entirely; `nemoclaw onboard` runs as a separate host process (via a new
`deploy/scripts/onboard-openclaw.sh`), reached from Compose's already-published
`mcp-tools:8004` and `gateway:8001` ports. This pivot is scoped to local
Docker Compose delivery only; `deploy/helm/nemoclaw/templates/agent-deployment.yaml`
and its NetworkPolicy are deleted with no K8s-native replacement in this ADR —
Kubernetes/OpenShell integration is deferred to a follow-up ADR.

## Context

**(a) Why replace ADR-010's design.** `agent/config.yaml`'s header —
*"NemoClaw agent configuration — wired up in M6. NemoClaw v0.0.56 / OpenShell
v0.0.44. Install: curl -fsSL https://www.nvidia.com/nemoclaw.sh |
NEMOCLAW_INSTALL_TAG=v0.0.56 bash"* — has referenced the real product since
before this session's work began, independently corroborating the live
verification performed this session (GitHub repo/API/raw content, npm, PyPI,
Discord, and direct reads of `docs.nvidia.com`/`docs.openclaw.ai`). Those
pinned versions are themselves stale by now; this ADR deliberately does not
carry them forward — installation targets NemoClaw's current last-known-good
(`lkg`) release channel and whatever OpenShell version it resolves as a
dependency, not the `v0.0.56`/`v0.0.44` pair `config.yaml` happened to name
at the time it was written. ADR-010's bespoke loop delivered the functional
behaviour (tool-calling, HITL-gated remediation) but never ran the actual
product `config.yaml` already named. Running the real product gets
actively-maintained sandbox hardening
(seccomp/Landlock/no-new-privileges/network isolation) the bespoke loop
never had, and closes a gap that predates this session.

**(b) Deployment topology.** `nemoclaw onboard` drives Docker directly to
build/manage its own OpenShell sandbox — it is not a container image to
`docker run`, and nesting it inside Compose would require Docker-in-Docker,
directly undermining OpenShell's own security purpose. It runs as a peer
host process instead, reaching the already-published `mcp-tools`/`gateway`
ports (`host.docker.internal` on macOS Docker Desktop;
`--add-host=host.docker.internal:host-gateway` or the bridge gateway IP on
Linux). This specific reachability path is unverified — see Negative
consequences.

**(c) Tool integration: MCP client in the plugin, not a REST wrapper.**
OpenClaw's tool system is plugin-based, not a native MCP client — "point at
an MCP URL" is not sufficient. A plugin manifest (`openclaw.plugin.json`
`contracts.tools`) declares owned tool names; runtime code registers
handlers via `api.registerTool()`. Two designs were considered:

- **Thin REST wrapper added to `mcp_tools` or a new sibling service** —
  rejected: duplicates the tool schema in two languages, adds a new service
  to deploy and health-check.
- **Plugin as an MCP client, speaking Streamable HTTP to the existing,
  unmodified `services/mcp_tools/server.py`** ✅ — Node.js has a first-class
  MCP client SDK; this is the same wire protocol `agent/tools.py`'s
  `MCPAgentTools` already used under ADR-010, so the server needs zero
  changes and the schema stays single-sourced from FastMCP's auto-generated
  `inputSchema`.

**(d) Preserving the ADR-004 HITL invariant — restated and extended.**
"The plugin only exposes what we register" is true for tools our plugin
controls, but real OpenClaw ships its own built-in tools (`exec`, `browser`,
`web_search`, `image_generate`, `message`) independent of any plugin —
capability the bespoke ADR-010 agent never had (its tool surface was exactly
the 7 named functions in `agent/tools.py` and nothing else). This is a
genuinely new attack surface, not a preserved one; the onboarding blueprint
must disable or tightly restrict these built-ins via OpenShell sandbox
policy, with equal weight to omitting `remediation.execute` from the plugin.

Separately: `agent/loop.py`'s `_await_approval_and_execute()` was
deterministic Python code, entirely outside the LLM's tool-calling surface,
that polled `GET /api/faults/{id}/token` and called `remediation.execute`
directly. That code has no home inside OpenClaw — an agent runtime must
never hold a secret it could leak into its own context. It moves into
`services/gateway/router.py`'s `post_decision()`, triggered synchronously on
approval: mint the token (unchanged), then call `remediation.execute`
server-to-server immediately, no polling, no LLM. This preserves every
property in ADR-004's Decision and every property ADR-010 added: the token
still never enters LLM context, is still minted only on operator click, is
still single-use and event-bound.

**(e) Standing Orders and cadence.** OpenClaw's `AGENTS.md` + "Standing
Orders" convention (permanent operating authority, documented
Authority/Trigger/Approval gate/Escalation syntax) maps directly onto our
fault-monitoring workflow. Heartbeat's documented 30-minute default is far
coarser than our current 5-second poll and unconfirmed to go sub-minute;
Cron is described for "precise timing" but is cron-syntax-based (likely
~1-minute floor). Neither reproduces live-demo pacing alone, so the primary
wake-up moves to a webhook fired by the Orchestrator/Gateway the instant a
scenario is injected (event-driven, arguably an improvement over the old
fixed-interval poll), with Cron retained only as a safety-net poll.

**(f) Persona and skills migration.** OpenClaw's SOUL.md convention matches
`agent/soul.md` by name and purpose; format is unconstrained markdown so no
structural rewrite is required, only provider-neutral language edits.
OpenClaw's skill frontmatter contract (`name`+`description` required) is
already satisfied by all 5 existing `SKILL.md` files, and — because ADR-010
already translated dotted MCP tool names to underscored function names for
its own OpenAI-schema requirements — the skill bodies already reference
exactly the tool names the new plugin registers, zero tool-name edits
needed. `infra-sentinel-guide`'s always-loaded orientation content folds
into `AGENTS.md` (confirmed unconditionally auto-injected every session)
rather than staying a 5th skill, since OpenClaw's skill discovery is
presumed more selective/on-demand than ADR-010's flat concatenation — to
confirm in the validation spike.

**(g) Kubernetes/Helm scope.** `nemoclaw onboard` drives Docker directly and
is not Helm/kubectl-shaped; NVIDIA's own docs point custom integrations at
raw OpenShell rather than the NemoClaw blueprint, signalling the reference
stack's design center is a single Docker host, not a K8s cluster. Following
this repo's own precedent for staging local-vs-shared-cluster gaps (ADR-006:
in-memory now, Redis prod later; ADR-003: CPU-only compose images now, GPU
LLM infra external/out of scope), this pivot is scoped to local Docker
Compose delivery only. `deploy/helm/nemoclaw/templates/agent-deployment.yaml`
and its NetworkPolicy are deleted with no replacement — a tracked
regression, not a silently-accepted gap.

**(h) Validation status.** Unlike ADR-010, which included a live vLLM
tool-calling spike before being written up as Accepted, this ADR has no live
validation run behind it yet. Given NemoClaw/OpenShell's novelty (created
March 2026) and the number of genuinely unverified integration points below,
a scripted validation spike is a hard prerequisite before implementation
begins, following the exact precedent ADR-010 set for its own unvalidated
tool-calling risk.

## Consequences

**Positive:**

- The lab runs a real, actively-maintained, NVIDIA-supported product instead
  of a hand-built look-alike carrying "NemoClaw" branding it didn't earn —
  and closes a gap `agent/config.yaml` has flagged since M6.
- `services/mcp_tools/`, `services/orchestrator/`, `services/simulator/`,
  `libs/common/pack_loader.py`, and all of `packs/` require zero code
  changes — they gain a new caller (the plugin) instead of losing their old
  one, and ADR-007/008's content-not-code and vertical-blind principles are
  fully preserved.
- ADR-010's dot-to-underscore tool-name translation, adopted purely to
  satisfy OpenAI-style function-name constraints, already produces exactly
  the tool names OpenClaw's plugin system needs — the 5 skill files require
  zero tool-name edits.
- The Gateway-triggered execution path removes the old harness's polling
  loop entirely: remediation now executes the instant a human clicks
  Approve, not up to `poll_interval` seconds later — a reliability
  improvement over ADR-010, not just a lateral move. Webhook-driven wake-up
  is a similar improvement on the detection side.
- Real, NVIDIA-documented support for our exact local vLLM setup (same
  `qwen3.6-35b-a3b` model family we already run) resolves ADR-003's
  "swappable LLM endpoint" goal with a supported product path, including a
  dedicated tool-calling-reliability doc directly addressing the risk
  ADR-010 flagged as unvalidated.
- Removes ~5 Python files and one Compose service's worth of bespoke
  LLM-loop code, plus already-dead cruft (`agent/snap.py`, only referenced
  by its own test; `agent/config.yaml`, never read by any code).

**Negative:**

- **Not yet technically validated.** No live test run has occurred, unlike
  ADR-010's live vLLM tool-calling spike. A validation spike (sandbox↔host
  Compose port reachability, Node MCP client vs. Python FastMCP server
  interoperability, SOUL.md discovery location, Cron/webhook granularity,
  built-in tool lockdown mechanism, SKILL.md extra-frontmatter-key
  tolerance, full live fault-to-resolution run) is a hard prerequisite
  before implementation begins.
- OpenClaw's tool system is plugin-based, not a native MCP client — a real
  TypeScript plugin (manifest + handler code + MCP client wiring) must be
  built and maintained, more integration work than "point at an MCP URL."
- Heartbeat's 30-minute default granularity is unusable for live-demo
  pacing; Cron's practical floor is likely ~1 minute. The design leans on a
  webhook trigger instead, whose ability to wake a full tool-capable agent
  turn is itself unverified.
- Real OpenClaw ships general-purpose built-in tools (`exec`, `browser`,
  `web_search`, `image_generate`) with no relationship to our plugin's
  allowlist — a new attack surface the bespoke ADR-010 agent never had by
  construction. Disabling/restricting these via blueprint or OpenShell
  policy is a hard requirement of this pivot, exact mechanism unconfirmed.
- The NemoClaw/OpenShell stack is very new (created March 2026); its
  interaction with a multi-service Docker-Compose-orchestrated lab, rather
  than a single personal-assistant use case, is genuinely novel territory.
- `services/gateway/router.py`'s `post_decision()` gains new, real logic
  (token retrieval + direct `remediation.execute` call + ported narration
  timing) — the only service-side logic change in this otherwise mostly
  additive pivot.
- `tests/e2e/test_full_loop.py` cannot be preserved as-is (imports
  `agent.llm`/`agent.loop`/`agent.tools` directly) and must be rewritten to
  exercise the Gateway's new execution trigger without an LLM in the loop;
  genuine LLM-tool-calling-loop coverage moves outside this repo's pytest
  suite entirely, to the plugin and the validation spike.
- Kubernetes/Helm integration is out of scope for this ADR.
  `agent-deployment.yaml` and its NetworkPolicy are deleted with no
  replacement, meaning the 30-tenant Helm deployment loses autonomous-agent
  capability entirely until a follow-up ADR designs a K8s-native
  OpenShell/OpenClaw story — `resourcequota.yaml`'s `persistentvolumeclaims: "0"`
  cap is a known future obstacle for whatever that follow-up needs.
- SOUL.md's exact required filesystem location is inferred by analogy to
  OpenClaw's documented skills-discovery precedence, not independently
  confirmed — to verify in the spike.
